# OpenSpec

`<docs>` — репозиторий документации продукта. Если отдельного нет — папка `docs/` основного репозитория.

Задачи change в Multica — навык `openspec-multica` или `npm.cmd run multica:sync`.

OpenSpec хранит поведение системы как требования со сценариями. `openspec/specs/` — как система работает сейчас,
`openspec/changes/<change>/` — что меняется. Change по PBC пишет аналитик, по ходу задач его обновляют
разработчики, после принятия PBC аналитик архивирует change: дельты вливаются в `specs/`.

## CLI

Команда — `openspec`. Нет в окружении — `npx -y @fission-ai/openspec@1.13.2` (одна версия на всех). Запускай
из корня клона `<docs>`. Флаги сверяй с `openspec <команда> --help`.

| Что | Команда |
|---|---|
| Инициализировать, если в `<docs>` нет `openspec/` | `openspec init --tools none` |
| Список changes и specs | `openspec list`, `openspec list --specs` |
| Посмотреть | `openspec show <имя> --type change\|spec` |
| Шаблон артефакта | `openspec instructions <proposal\|specs\|design\|tasks> --change <имя>` |
| Проверить | `openspec validate <имя> --strict --no-interactive` |
| Архивировать | `openspec archive <имя> --yes` |

Если в `openspec/config.yaml` `<docs>` есть свои правила (контекст проекта, язык, требования к артефактам),
они главнее этого скилла. Инициализирует `openspec/` только аналитик: нет каталога — спроси его.

## Change по PBC

Один PBC — один change: `openspec/changes/pbc-<capability>/`. Доработки и баги вне PBC — раздел «Change вне PBC». Создай его через CLI, если версия умеет
(`openspec new change pbc-<capability>`), иначе — каталог вручную.

```
openspec/changes/pbc-<capability>/
├── proposal.md
├── specs/<capability-path>/spec.md   # дельта на каждую затронутую capability
├── design.md
└── tasks.md
```

### proposal.md

```markdown
# Proposal

PBC: `docs/pbc/<capability>/README.md`. PRD: <версия>.

## Why
1–2 предложения из раздела 1 PBC.

## What Changes
- … (из разделов 2 и 11). Ломающее — **BREAKING**.

## Capabilities
### New Capabilities
- `<capability-path>`: <что описывает>
### Modified Capabilities
- `<существующий путь из openspec/specs/>`: <что меняется>

## Impact
API (раздел 4), данные (3), события (5), зависимости (6), затронутые PBC.
```

### Delta spec

```markdown
## Purpose
<только для новой capability: 1–2 предложения, от 50 символов>

## ADDED Requirements

### Requirement: <название>
Система MUST <поведение>.

#### Scenario: <название>
- **GIVEN** <контекст>
- **WHEN** <действие>
- **THEN** <наблюдаемый результат>
- **AND** <ещё результат>
```

- Требования — из Gherkin-критериев раздела 11, пунктов DoD раздела 12, контрактов раздела 4 и НФТ раздела 8.
  Gherkin истории переносится в сценарий: Given → **GIVEN**, When → **WHEN**, Then → **THEN**.
- В каждом требовании — нормативное слово `MUST` или `SHALL` латиницей, остальной текст по-русски. Описание
  требования — до 500 символов.
- Хотя бы один сценарий на требование. Заголовок сценария — ровно `#### Scenario:`: с тремя решётками или списком
  сценарий молча теряется.
- `## MODIFIED Requirements` — целиком скопированный из `openspec/specs/` блок требования с правками.
  `## REMOVED Requirements` — с **Reason** и **Migration**. `## RENAMED Requirements` — `FROM:` / `TO:`.
- Никакой реализации в спеке: классы, таблицы, файлы — в `design.md`.

### design.md

`# Design`, затем `## Context`, `## Goals / Non-Goals`, `## Decisions` (решение, альтернативы, почему),
`## Risks / Trade-offs` (`[риск] → смягчение`), при необходимости `## Migration Plan` и `## Open Questions`.
Источник — разделы 3–9 PBC, технические заметки техлида из валидации и ADR. Технических решений сам не придумывай:
чего нет в заметках техлида и ADR — вопрос техлиду.

### tasks.md

```markdown
# Tasks

## 1. <логическая часть: API сущности, экран, CI…>

- [ ] 1.1 <что сделать> — проверка: <как убедиться, что сделано>
- [ ] 1.2 …

## N. Интеграционные проверки

- [ ] N.1 …
```

Группа — законченная логическая часть: всё, что нужно, чтобы она заработала, — модели и миграции, сервисы, guards
и middleware, API, интерфейс, тесты и документация. По слоям не дели: «данные», «API», «интерфейс» отдельными
группами — нет. Группы — по порядку зависимостей. Пункт — небольшой и проверяемый. Лид режет задачи разработки
по группам: задача закрывает одну или несколько групп целиком.

### Проверка

`openspec validate pbc-<capability> --strict --no-interactive` без ошибок; каждый критерий приёмки PBC стал
сценарием; `openspec show pbc-<capability> --type change` читается без потерь.

## Change вне PBC

Доработка — свой change `<ключ issue>-<slug>` в нижнем регистре (например, `prj-42-export-csv`), той же структуры;
`design.md` — если есть технические решения. Пишет аналитик (скилл `change-request`), архивирует после верификации.
Техзадача без изменения поведения change не требует.

## Правка спецификации при исправлении бага

Аналитик решил, что спецификация молчит или ошибочна, и согласовал правку (скилл `change-request`):

- требование уже меняет активный change (PBC в разработке или доработка, `openspec list`) — правь этот change;
- иначе — change `<ключ issue>-<slug>` с дельтой (`ADDED` сценарий или `MODIFIED` требование) и архивация в том же MR
  по разделу «Архивация»: спецификация обновляется вместе с исправлением.

## Разработчик по ходу задачи

Change задачи — тот, что указан в её разделе «Спецификация» (`pbc-<capability>` или `<ключ>-<slug>` доработки).
Отдельного MR в `<docs>` на каждую задачу нет:

- пункты `tasks.md` не отмечай: прогресс задач виден в Multica, пункты отметит аналитик при архивации;
- реализация разошлась с `design.md` — решение согласуй с техлидом и опиши в MR в код, раздел «Отступления
  от design.md»; в `design.md` его перенесёт аналитик при архивации;
- задача меняет требования или сценарии и аналитик согласился в issue задачи — MR в `<docs>` из ветки
  с тем же именем, что у MR в код, и `openspec validate <change> --strict --no-interactive`.

## Change следующего PBC

Change следующего PBC пишется, пока предыдущий в разработке, и его блоки `MODIFIED` могут устареть. Перед передачей
в разработку — после того как предыдущий change архивирован — перебазируй ветку на свежий `main`, сверь `MODIFIED`
с обновлёнными `openspec/specs/` и прогони `validate --strict`.

## Архивация

Изменения могут идти параллельно: PBC в разработке, доработки, правки при багах. Блок `MODIFIED`, скопированный
до чужой архивации, при своей архивации целиком заменит требование и сотрёт чужую правку. Поэтому перед любой
архивацией: rebase ветки на свежий `main`, сверь каждый блок `MODIFIED` с текущим `openspec/specs/` и перенеси в него
изменения, влитые после копирования, затем `openspec validate <change> --strict --no-interactive`.

После того как аналитик принял PBC или доработку: в ветке архивации отметь пункты `tasks.md` по влитым задачам
(неотмеченное — объяснено в issue) и перенеси в `design.md` отступления из описаний влитых MR задач (раздел
«Отступления от design.md»). Затем `openspec archive <change> --yes` и проверь, что дельты попали в `openspec/specs/`, а change — в
`openspec/changes/archive/`. MR в `<docs>` из ветки `docs/<ключ issue PBC>-archive-<capability>`, вливает человек.
