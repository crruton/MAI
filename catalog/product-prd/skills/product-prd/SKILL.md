# PRD

`<docs>` — репозиторий документации продукта. Если отдельного нет — папка `docs/` основного репозитория.

PRD — полное описание продукта для агентной разработки: что строим, для кого, зачем, в каких границах и как поймём,
что получилось. Пишет владелец продукта по brief'у и интервью с заказчиком. Как именно реализовать, PRD задаёт
на уровне требований и ограничений; технические решения принимает техлид (ADR).

## Где лежит

| Что | Путь в `<docs>` |
|---|---|
| Brief заказчика, как получен | `docs/brief/YYYY-MM-DD-<slug>.md` |
| PRD | `docs/prd/NN-<slug>.md`, набор файлов ниже |
| Журнал изменений | `CHANGELOG.md` в корне |

Ветка — `docs/<ключ issue PRD>-prd-<slug>`: по ключу CI после вливания пишет «влито» в issue. Коммиты —
`docs(prd): <что сделано>`. Если в `<docs>` уже есть свои соглашения,
они главнее этого раздела.

## Состав

Документы пронумерованы и самодостаточны. Раздел, который продукту не нужен (например, видео или монетизация),
не создаётся, а в `00-overview.md` в «Как читать» сказано, почему его нет. Нумерацию не сдвигай.

| Файл | Что в нём |
|---|---|
| `00-overview.md` | шапка (продукт, версия PRD, дата, статус); назначение; как читать и зависимости документов; ключевые продуктовые решения — нумерованный список; допущения `A1…An`, которые требуют подтверждения; глоссарий |
| `01-vision-positioning.md` | однострочное описание; видение; конкурентный анализ — таблица «конкурент / что делает / где сильны / где наш зазор» и вывод; УТП; стратегия выхода на рынок |
| `02-personas.md` | персоны `P1…Pn`: кто, задачи, боли, как пользуется продуктом, права |
| `03-functional-scope.md` | полный функциональный скоуп по модулям `M1…Mn`: что входит в модуль |
| `04-architecture.md` | принципы и каркас системы, ключевые компоненты, интеграции, стек — как требования и ограничения |
| `05-data-model.md` | ключевые сущности предметной области и связи; что общее, что приватное |
| `06-…`, `07-…` | доменные алгоритмы и пайплайны, если они ядро продукта (ML, обработка данных) |
| `08-api-spec.md` | ключевые внешние контракты и эндпоинты, если продукт их предоставляет |
| `09-nfr-security-compliance.md` | производительность, изоляция, роли и доступ, приватность и compliance, надёжность — с числами |
| `10-user-stories.md` | user stories по эпикам с критериями приёмки (формат ниже) |
| `11-monetization-billing.md` | сегменты, потоки выручки, тарифы, открытые вопросы |
| `12-metrics.md` | метрики успеха по фазам зрелости продукта и принципы измерения |
| `13-roadmap.md` | сводная таблица приоритетов `P0–P3`, фазы поставки, стратегия (PoC-first, инкременты) |

Технические разделы (04–08) владелец продукта пишет на уровне требований и может попросить техлида проверить их
или дополнить.

## User stories

~~~markdown
## Эпик A. <название>

### US-A1 (P0) — <коротко>
*Как <роль из 02-personas>, я хочу <действие>, чтобы <ценность>.*
```gherkin
Given <контекст>
When <действие>
Then <наблюдаемый результат>
And <ещё результат>
```
~~~

- ID `US-<эпик><номер>` не переиспользуются. Приоритет `P0–P3` — тот же, что в `13-roadmap.md`.
- Критерии проверяемы снаружи и пригодны для QA: без «удобно», «быстро» без чисел.
- Кроме основного сценария — ошибки, права доступа, пустые и граничные данные, если важны для истории.

## Пометки

Для продукта, который уже частично реализован, отмечай состояние: `PoC` — делается в текущем срезе, `TARGET` —
целевой дизайн, не реализован, «реализовано» — есть в коде. Расхождение PRD с кодом не скрывай — помечай.

## Версии

- В шапке `00-overview.md` — версия PRD и дата. Первый согласованный PRD — `1.0`, существенное изменение
  объёма — следующая мажорная версия, уточнения — минорная.
- Каждое изменение PRD — запись в `CHANGELOG.md`: дата, версия, что изменилось и почему, какие разделы.
- Решение заказчика, принятое в интервью, попадает в «Ключевые продуктовые решения» или закрывает допущение.

## Чек-лист качества

PRD готов, когда:

- есть все нужные продукту разделы, отсутствие остальных объяснено в `00-overview.md`;
- проблема, персоны и ценность понятны; конкурентный анализ опирается на источники;
- каждый модуль `03` покрыт user stories `10`, у каждой истории есть приоритет и Gherkin-критерии;
- нефункциональные требования и метрики заданы числами, метрики разложены по фазам;
- roadmap связывает приоритеты с историями;
- допущения перечислены, а вопросы, которые меняют объём, приоритеты или ограничения, закрыты ответами заказчика;
- термины из глоссария используются одинаково во всех документах, ссылки между документами не битые;
- версия и `CHANGELOG.md` обновлены.
