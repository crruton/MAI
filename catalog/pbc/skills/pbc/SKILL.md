# PBC

`<docs>` — репозиторий документации продукта. Если отдельного нет — папка `docs/` основного репозитория.

PBC — капабилити продукта со своими границами: она владеет своими данными, предоставляет API и события,
обслуживает свою часть пользовательского процесса и реализуется и принимается целиком. PBC выводится из PRD:
модули `03-functional-scope.md` и user stories `10-user-stories.md` раскладываются по капабилити.

## Где лежит

| Что | Путь в `<docs>` |
|---|---|
| Индекс PBC: разрез, порядок, статус | `docs/pbc/README.md` |
| Шаблон | `docs/pbc/_TEMPLATE.md` — раздел «Шаблон» ниже, создай, если нет |
| Worksheet PBC | `docs/pbc/<capability>/README.md` |
| Дополнительные документы PBC | `docs/pbc/<capability>/<тема>.md` |
| Тест-кейсы QA | `docs/pbc/<capability>/test-cases.md` |
| OpenSpec change PBC | скилл `openspec` |

`<capability>` — короткое имя в kebab-case (`search`, `identity`, `tenancy-billing`). Оно же — ключ PBC в issue:
«PBC: <capability> — <название>». Ветка MR — `docs/<ключ issue PBC>-pbc-<capability>`: по ключу CI после вливания пишет «влито» в issue PBC.
Коммиты — `docs(pbc): <что сделано>`.
Если в `<docs>` уже есть свои соглашения, они главнее этого раздела.

## Как резать PRD

- Граница PBC — граница владения данными и ответственности: у каждой сущности `05-data-model.md` один владелец,
  остальные читают её через API или события.
- Каждый модуль `03` и каждая user story `10` принадлежат ровно одному PBC. Сквозное (арендность, доступ,
  биллинг) — отдельные PBC.
- PBC реализуется и принимается целиком, поэтому его размер — то, что один разработчик сделает
  за обозримый срок. Большая капабилити — режь на PoC-срез и `TARGET`, в разработку идёт срез.
- Порядок — по зависимостям и приоритетам `P0 → P3`: сначала то, на чём стоят остальные.

## Индекс `docs/pbc/README.md`

```markdown
# PBC — Packaged Business Capabilities

PRD: <версия>. Каждый PBC прорабатывается по `_TEMPLATE.md` в `docs/pbc/<capability>/README.md`.

## Разрез
| PBC | Обслуживает (этап процесса) | Модули PRD | User stories | Зависит от |
| --- | --- | --- | --- | --- |
| `identity` | … | M1 | US-A1, US-A2 | — |

## Порядок реализации
1. `identity` — <почему первым>
2. …

## Статус
| PBC | Статус | Issue |
| --- | --- | --- |
| `identity` | готов к разработке / в разработке / реализован / не начат | <ссылка> |
```

Разрез — часть первой валидации: владелец продукта и техлид проверяют индекс вместе с первым PBC.

## Шаблон

```markdown
# PBC: <Название капабилити>

> Worksheet по `docs/pbc/_TEMPLATE.md`. PRD: <версия>. Пометки: `PoC` / `TARGET`.

## 1. Назначение и ценность
Зачем эта капабилити, какую часть пользовательского процесса обслуживает, какую ценность даёт пользователю
и бизнесу.

## 2. Bounded context (границы)
Что входит в капабилити и что **явно не входит** (где граница с соседними PBC). Ключевой шов.

## 3. Данные, которыми владеет
Сущности из `docs/prd/05-data-model.md`, которые принадлежат этому PBC: общие или приватные, кто ещё их читает
(только через API или события). Таблица «сущность / PoC или TARGET / природа».

## 4. API (контракты)
Ключевые эндпоинты (из `docs/prd/08-api-spec.md` или новые): метод, путь, вход и выход, ошибки.

## 5. События (publish / subscribe)
Какие доменные события публикует и на какие подписывается.

## 6. Зависимости
От каких PBC и внешних систем зависит и что от них получает.

## 7. Алгоритмы (если есть)
Ссылка на `docs/prd/06-…`; специфика алгоритмов и моделей этого PBC, метрики качества.

## 8. НФТ и безопасность
Производительность, изоляция, доступ, приватность — что относится именно к этому PBC (`docs/prd/09-…`), с числами.

## 9. Деградация данных
Как капабилити ведёт себя, когда данных не хватает или зависимость недоступна.

## 10. Риски и открытые вопросы
Что требует подтверждения — со ссылкой на допущения PRD.

## 11. Бэклог (по приоритетам)
User stories из `docs/prd/10-user-stories.md` с их Gherkin-критериями, по приоритетам `P0–P3`. Для каждой —
что входит в PoC-срез. Уточнённые критерии PBC — тоже Gherkin, с ID `US-…` исходной истории.

## 12. Definition of Done
Проверяемые критерии завершённости капабилити — по ним QA пишет тест-кейсы, а аналитик принимает PBC.
```

## Критерии приёмки

Критерии приёмки PBC — Gherkin-критерии историй раздела 11 и пункты раздела 12. Каждый проверяем снаружи:
наблюдаемый результат на экране, в ответе API, в данных, в логе; числа вместо «быстро» и «удобно». Кроме основного
сценария — ошибки, права доступа, пустые и граничные данные, деградация из раздела 9. Перед валидацией критерии
просматривает QA: проверяемы ли они и чего не хватает.

## Валидация

Аналитик зовёт владельца продукта и техлида одним комментарием в issue PBC со ссылкой на MR. Каждый отвечает
комментарием-вердиктом:

```markdown
**<Роль>: замечаний нет**
```

или

```markdown
**<Роль>: замечания (N)**
1. [блокер] §4 — <что не так> → <что предлагаю>
2. [замечание] §11, US-B2 — …
```

`[блокер]` — без исправления PBC не готов, `[замечание]` — стоит исправить. Аналитик ждёт оба вердикта раунда,
исправляет всё и зовёт обоих снова — каждый проверяет исправления и то, что изменилось. Раунд без сходимости
третий раз подряд — аналитик выносит разногласие человеку.

### Бизнес-валидация (владелец продукта)

- Разрез соответствует PRD: всё из модулей и историй, отнесённых к PBC, покрыто, лишнего нет.
- Назначение и ценность совпадают с целями и персонами PRD.
- Границы не режут пользовательский сценарий так, что его нельзя принять.
- Бизнес-правила и критерии приёмки совпадают с ожиданием бизнеса; приоритеты историй совпадают с PRD.
- Риски и открытые вопросы, которые решает бизнес, названы.

### Техническая валидация (техлид)

- Реализуемость: данные, API, события и зависимости непротиворечивы и встраиваются в текущую архитектуру и ADR.
- Владение данными однозначно, контракты между PBC согласованы с соседями.
- НФТ достижимы, деградация описана, риски безопасности учтены.
- Нужны ли ADR, новые библиотеки, миграции — названо.
- Оценка объёма и технические заметки для лида: подход, затронутые модули, риски, что делать первым.

## PBC готов

- Оба вердикта последнего раунда — «замечаний нет».
- Для PBC написан OpenSpec change, `openspec validate --strict` проходит.
- MR с worksheet и OpenSpec change влит человеком в `main` `<docs>`.

## Очередь в разработку

В разработке одновременно один PBC. Следующий уходит лиду, только когда предыдущий реализован и принят
аналитиком. Готовые PBC ждут в порядке из индекса. Готовить следующие PBC, пока текущий в разработке, можно и нужно.

## Верификация реализованного PBC

По каждому критерию приёмки (Gherkin раздела 11 и пункт раздела 12) и каждому requirement OpenSpec change:
выполнен, не выполнен или не проверен, и доказательство — тест-кейс из отчёта QA, MR, наблюдаемое поведение.
Документация в `<docs>` описывает то, что реализовано.

```markdown
| Критерий | Результат | Доказательство |
|---|---|---|
| US-B1 / AC 1 | выполнен | TC-3 passed, MR !123 |
| DoD 4 | не выполнен | TC-7 failed, баг <ссылка> |
```
