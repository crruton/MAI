# Нарезка PBC на задачи

`<docs>` — репозиторий документации продукта. Если отдельного нет — папка `docs/` основного репозитория.

Здесь задачи режутся по логике. Другой вариант — по времени: не больше 2 рабочих дней middle-разработчика на задачу, вертикальный срез, если влезает. Команда выбирает один вариант и держит его в `AGENTS.md` проекта.

## Вход

Worksheet PBC (`docs/pbc/<capability>/README.md`), OpenSpec change `pbc-<capability>` (specs, `design.md`,
`tasks.md`), технические заметки и оценка техлида из валидации PBC, ADR, тест-кейсы QA, если уже есть. Для доработки —
постановка в issue, её change `<ключ>-<slug>` и заметки техлида; для техзадачи — описание и подход техлида.

## Граница задачи

Режь по логике, а не по времени и не по слоям. Задача — законченная часть функциональности: после вливания она
работает целиком и проверяется отдельно — тестами, запросом к API, экраном. Предела по дням нет, размер MR
не ограничен.

| Задача | Что в неё входит |
|---|---|
| API сущности (или нескольких тесно связанных сущностей одного агрегата) | модели и миграции, слой работы с записями в БД, сервисы бизнес-логики, guards и middleware, если нужны, REST API с валидацией входа, тесты |
| Интерфейс капабилити | экраны и компоненты, состояние, вызовы API, тесты. Небольшой сценарий — одна форма к одному API — вместе с этим API |
| Сквозной механизм: аутентификация, права, аудит, обработка ошибок | механизм целиком: модели, сервисы, guards и middleware, подключение к маршрутам, тесты |
| CI и сборка | весь пайплайн: линтеры, тесты, сборка, кэш, артефакты, деплой стенда |
| Каркас проекта | структура, конфигурация, окружение разработки, базовые зависимости |
| Интеграция с внешней системой | клиент, маппинг данных, повторы и ошибки, конфигурация, тесты |

Объединяй в одну задачу:

- части одной функциональности на разных слоях: модель без API, API без guards, guard без маршрутов, которые
  он защищает, — не задачи;
- всё про одну подсистему: CI, линтеры, конфиг сборки — одна задача, а не несколько;
- то, что по отдельности не проверить: после вливания такой задачи QA нечего проверять.

Отдельная задача — только на настоящей границе:

- разные сущности или капабилити, которые работают и проверяются независимо;
- то, на чём стоят несколько других задач, — механизм прав нужен API всех сущностей: отдельно и раньше;
- интерфейс отдельно от API, когда экранов много, а API нужен раньше;
- неизвестное, которое не даёт спланировать, — сначала задача-исследование (spike) с результатом: решение
  или подход.

Независимые капабилити ради меньшего числа задач не склеивай: у задачи один смысл, по заголовку понятно, что
заработает.

Пункты и группы `tasks.md` OpenSpec — не границы задач. Задача закрывает все пункты своей логической части, из каких
бы групп они ни были.

Задача — один исполнитель и один MR в код, плюс MR в `<docs>`, только если задача меняет требования
или сценарии OpenSpec. Оценка в задаче
нужна для плана и порядка, а не как предел размера. Сомневаешься в оценке или в том, где граница, — спроси
техлида в issue PBC.

Перед заведением сверь план:

- нет двух задач, которые ради одной цели правят одну сущность или подсистему;
- нет задачи из одного слоя: только модели, только миграции, только guards, только часть настройки CI;
- каждую задачу можно проверить после вливания, не дожидаясь других незавершённых задач.

## Описание задачи

Заголовок: `[<capability>] NN. <что сделать>` для PBC, `[<ключ доработки>] NN. <что сделать>` для доработки,
где `NN` — номер в плане. Описание:

```markdown
## Цель
<какую часть PBC закрывает и зачем>

## Что сделать
<все части логической единицы, которые в ней есть: модели и миграции, слой БД, сервисы, guards
и middleware, API, интерфейс>
- …
## Не входит
- …

## Спецификация
- OpenSpec: требования и сценарии `<имена>`, пункты `tasks.md` `1.1, 1.2`
- PBC: раздел и история `US-…`

## Затронутое
Модули, API, данные — из заметок техлида и `design.md`.

## Зависит от
<задачи плана, которые должны быть влиты раньше> | нет

## Definition of Done
- код и тесты к новой логике, CI зелёный
- отступления от `design.md` перечислены в описании MR
- <критерии, которые проверит QA>

## Оценка
<часы или дни> — <из чего складывается>
```

В Definition of Done задачи — только проверки, которые агент выполнит сам: тесты, CI, запросы к API на локально
поднятом сервисе. Проверки на stage, на живых внешних сервисах и в браузере на стенде — в DoD PBC: при проверке
влитой задачи их не на чем выполнить, и задача повиснет в ожидании человека.

## Порядок и приоритеты

1. Построй граф зависимостей: что от чего зависит по данным, контрактам и коду.
2. Порядок: сначала критический путь и то, на чём стоят остальные (каркас, CI и сквозные механизмы → API сущностей
   в порядке зависимостей данных → интерфейс → интеграции), рискованное и неизвестное — раньше. Внутри — по приоритету историй PBC
   (`P0` раньше `P1`).
3. Приоритет issue: `urgent` — блокирует критический путь сейчас, `high` — истории `P0`, `medium` — `P1`, `low` —
   остальное. Флаг приоритета сверяй с `multica issue create --help`.
4. Исполнитель всех задач — разработчик squad'а, он один: задачи идут друг за другом в порядке плана.

## План

Комментарий в issue PBC:

```markdown
## План PBC <capability>

| № | Задача | Оценка | Приоритет | Зависит от | Исполнитель | OpenSpec |
|---|---|---|---|---|---|---|
| 01 | … | 1 д | high | — | Developer 1 | 1.1, 1.2 |

Критический путь: 01 → 03 → 05. Итого: N дней.
Покрытие: каждый критерий приёмки PBC и каждый пункт `tasks.md` — в какой задаче.
```

## Заведение и выпуск

- Все задачи — sub-issue PBC или доработки, сразу с исполнителем и статусом `backlog`: в `backlog` задача назначена,
  но агента не будит. Баг и техзадача на одну задачу — сама issue, без sub-issue.

  ```bash
  multica issue create --parent <pbc-или-доработка-issue-id> --project <project-id> --assignee "<разработчик>" \
    --status backlog --title "[<capability>] 01. <что сделать>" --description-file ./task-01.md
  ```

- Выпуск — перевод в `todo`: `multica issue status <id> todo`. Это будит разработчика.
- У разработчика одна текущая задача в `todo` или `in_progress`. Следующую он берёт из `backlog` сам, когда
  текущая ушла на ревью или влита, — по «Одной очереди» и только со влитыми зависимостями. Лид выпускает задачу,
  только когда у разработчика нет текущей: первую задачу плана, баг, техзадачу.
- Поэтому порядок держится на плане: номер `NN` в заголовке, приоритет issue и «Зависит от» в описании должны быть
  точными.

## Одна очередь

Задачи приходят из PBC в разработке, доработок, багов и техзадач, а разработчик один. Следующую задачу разработчик
берёт сам, а лид выпускает в таком порядке:

1. баги `blocker` и `critical` — они перебивают план;
2. задачи с приоритетом `urgent`, который поставил человек;
3. следующая задача плана PBC;
4. доработки, остальные баги и техзадачи — по приоритету, при равном — кто раньше пришёл.

Не давай одной очереди голодать: если пункт 4 ждёт дольше двух задач PBC подряд, он идёт следующим. Порядок можно
поменять по просьбе человека: лид меняет приоритеты задач.

## Перепланирование

План меняется, когда разработчик сообщает, что граница задачи неверна (нужна часть из другой задачи или задача
распадается на независимые), когда QA нашёл баг,
когда изменился PBC. Обнови план в issue PBC: что изменилось и почему.
