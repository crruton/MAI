# Тестирование

`<docs>` — репозиторий документации продукта. Если отдельного нет — папка `docs/` основного репозитория.

## Тест-кейсы

Файл `docs/pbc/<capability>/test-cases.md` в `<docs>`, ветка `docs/<ключ issue PBC>-test-cases-<capability>`. Источники:
Gherkin-критерии историй раздела 11 PBC, пункты DoD раздела 12, сценарии OpenSpec change `pbc-<capability>`,
деградация из раздела 9 и НФТ из раздела 8.

```markdown
# Тест-кейсы: PBC <capability>

## Покрытие
| Критерий | Тест-кейсы |
|---|---|
| US-B1 / AC 1 | TC-1, TC-2 |
| DoD 3 | TC-5 |
| OpenSpec: <requirement> / <scenario> | TC-1 |

## TC-1: <название>
- Тип: основной | альтернативный | негативный | граничный | НФТ | регрессия
- Покрывает: US-B1 / AC 1; OpenSpec <scenario>
- Актор и права: <роль>
- Предусловия: <данные, состояние системы>
- Тестовые данные: <конкретные значения>

| # | Действие | Ожидаемый результат |
|---|---|---|
| 1 | … | … |

- Постусловия: <что изменилось в системе>
- Автоматизация: unit | API | e2e | ручной — <где лежит автотест>
```

Каждый критерий приёмки покрыт хотя бы одним тест-кейсом. Критерий нельзя проверить или тест-кейс не выводится
из PBC — PBC неполон: вопрос аналитику. Техники: классы эквивалентности и граничные значения, таблица решений для
бизнес-правил, переходы состояний для сценариев, матрица ролей для доступа, негативные — неверный ввод, нет прав,
повторное действие, недоступная зависимость.

## Окружение

Систему целиком поднимаешь для тестирования PBC, проверки доработки и бага вне PBC в разработке. Проверка
влитой задачи обходится без этого — см. её раздел.

Есть описанный в `<docs>` стенд, на который выкатывается `main`, — проверяй на нём. Нет — возьми свежий `main`
кода, собери и запусти систему по README репозитория и `<docs>` у себя в рабочем каталоге. API
проверяй запросами, интерфейс — браузером без экрана (Playwright), если он доступен. Чего проверить нельзя, так и пиши: «не проверено»
и почему. Машину делят другие агенты: поднимай систему на свободных портах и со своими данными, после проверки
останови всё, что запустил.

## Проверка влитой задачи

Лёгкая проверка: систему целиком не поднимай, браузер не открывай. Интерфейс и сквозные сценарии проверяются
при тестировании PBC и проверке доработки.

1. MR влиты: `state: merged`, коммит есть в `main`. Пайплайн `main` на этом коммите зелёный; не завершён — дождись
   его конца: `glab ci status --branch main --live` или `glab api projects/:id/pipelines?sha=<коммит>`.
2. В MR есть тесты к новой логике и к Definition of Done задачи. Прогони на свежем
   `main` автотесты затронутых модулей — они проходят. Весь набор уже прогнал пайплайн.
3. Задача меняет API — проверь его запросами по сценариям OpenSpec, на которые она ссылается. Подними для этого
   только сервис с этим API и то, без чего он не стартует, или проверь интеграционными тестами проекта.
4. Критерий, который проверяется только через интерфейс или сквозной сценарий, здесь не проверяй: в отчёте —
   «проверю при тестировании PBC» (у задачи доработки — «при проверке доработки»).
5. Чего нельзя проверить в окружении (нет Docker, stage, внешних сервисов), — «не проверено: нет окружения»
   в отчёте и пункт в план тестирования PBC. Задачу это не блокирует.
6. Отчёт — комментарий в issue задачи (формат ниже), окружение — «автотесты и API».

Исправление бага проверяй так же: в MR есть тест, который воспроизводит баг, и он проходит. Баг не из PBC или
доработки в разработке — их тестирования не будет, поэтому воспроизведи его по шагам из issue в окружении
из раздела «Окружение», убедись, что он ушёл, и проверь регрессию вокруг.

## Тестирование PBC

Когда влиты все задачи PBC:

1. Свежий `main`, все автотесты.
2. Все тест-кейсы PBC; каждая user story раздела 11 — от начала до конца, как пользователь. Сюда же — всё, что
   проверки влитых задач отложили до PBC.
3. DoD раздела 12, НФТ раздела 8 — измерением, деградация раздела 9 — где воспроизводима.
4. Регрессия: основные сценарии соседних PBC, которые зависят от этого или от которых зависит он.
5. Отчёт — комментарий в issue PBC.

После исправления багов — повтор упавших тест-кейсов и регрессия вокруг исправлений.

## Подтверждение бага от человека

Баг пришёл от человека без шагов или без ожидаемого результата:

1. Воспроизведи на свежем `main` по описанию. Не воспроизводится — вопросы автору одним комментарием (окружение,
   данные, точные шаги), issue в `blocked`.
2. Найди, как должно быть: требование и сценарий OpenSpec, раздел PBC, история PRD. Спецификация молчит или
   противоречит ожиданию автора — спроси аналитика: баг это или доработка.
3. Дополни issue по формату бага ниже: шаги, ожидаемый и фактический результат, источник ожидаемого, окружение
   и коммит, серьёзность.

## Проверка доработки

Когда закрыты все задачи доработки: каждый критерий приёмки постановки и каждый сценарий её OpenSpec change — по шагам,
плюс регрессия затронутых сценариев. Задача была одна и её проверка уже покрыла всё — сошлись на тот отчёт, повторять
не нужно.

Доработка меняет поведение, которое покрывают тест-кейсы капабилити, — обнови `docs/pbc/<capability>/test-cases.md`
своим MR (ветка `docs/<ключ доработки>-test-cases-<capability>`): иначе следующая регрессия даст ложные баги.
Исправленный баг, которого тест-кейсы не ловили, — добавь регрессионный тест-кейс тем же способом.

## Отчёт

```markdown
## Проверка: <задача или PBC>

Коммит `main`: <sha>. Окружение: <стенд или локально>. Дата: <дата>.

| Что | Результат | Доказательство |
|---|---|---|
| TC-1 / OpenSpec <scenario> | passed | <команда и вывод или шаги> |
| TC-4 | failed | баг <ссылка> |

Не проверено: <что и почему>.
Итог: проверено, замечаний нет | найдены баги: N (блокеров: K).
```

## Баг

Найден при проверке PBC или его задачи — sub-issue PBC без исполнителя, заголовок `[<capability>] Баг: <кратко>`;
найден при проверке доработки или в уже реализованном — sub-issue доработки или отдельная issue «Баг: <кратко>».
Всегда с упоминанием лида — назначает баг он.

- Шаги воспроизведения, ожидаемый и фактический результат.
- Окружение и коммит, задача, в которой найден, тест-кейс, критерий приёмки или сценарий OpenSpec.
- Серьёзность: `blocker` — PBC нельзя принять, `critical`, `major`, `minor`.
- Логи и вывод команд — фрагментом, без токенов и персональных данных.
