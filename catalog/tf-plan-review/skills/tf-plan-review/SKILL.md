# Terraform plan review

Return findings ordered by impact, each tied to a resource address and evidence, plus a clear statement of remaining uncertainty. Establish the project's owning repository, authorized runner, backend, target and change owner.

## Execution boundary

A reviewed plan is not human approval to apply it. Replacement, deletion and consequential in-place changes must remain visible in the concrete plan presented for approval.

## Verify what the artifact represents

1. Establish commit, root directory, account/project, backend/state key, workspace, variable sources, Terraform/provider versions and plan time. Compare these with the intended environment. A plan without target identity is insufficient for a release decision.
2. Identify mode and flags: normal, refresh-only or destroy; `-target`, `-replace` and `-refresh=false` materially change its meaning. A targeted or non-refreshed plan cannot establish that the complete environment is safe.
3. Use the plan generated by the project runner or generate one there with the exact inputs. Saved plans, JSON, state, logs and output changes may contain plaintext secrets; keep full artifacts restricted and send only a sanitized review into chat or an MR.
4. Inspect repository hooks and external data programs before executing planning locally. Planning reads providers/data sources and may run external code; a plan command is not an isolation boundary.

## Extract structure without dumping values

On the trusted runner, with shell pipeline error handling enabled, this local projection omits before/after values:

```bash
terraform show -json tfplan | jq '{
  format_version,
  terraform_version,
  changes: [.resource_changes[]? | {
    address, previous_address, mode, provider_name, action_reason,
    actions: .change.actions,
    replace_paths: .change.replace_paths,
    importing: (.change.importing != null),
    has_unknowns: ([.change.after_unknown | .. | select(. == true)] | length > 0)
  }],
  output_names: ((.output_changes // {}) | keys)
}'
```

This is a first-pass inventory, not a complete redactor or review. Addresses/map keys and output names can also carry sensitive identifiers; review them before sharing. Check the producer's JSON format version and successful exit status. Inspect needed values only within the approved restricted environment and summarize their semantics without exposing credentials.

## Review consequences

1. **Deletion/replacement:** handle both `["delete", "create"]` and `["create", "delete"]`. Trace `replace_paths` and `action_reason`; replacements can also come from taint or explicit requests. Establish data ownership, backups/restore evidence, downtime and dependent resources. Create-before-destroy does not guarantee capacity, name uniqueness or uninterrupted service.
2. **Identity movement/adoption:** check `previous_address`, imports and changed collection keys. Explain whether this is an address move, adoption, real creation or accidental loss of association. Compare code intent to planned remote changes.
3. **In-place updates:** inspect IAM grants, firewall routes, TLS/auth settings, encryption, retention and database parameters. An `update` can revoke access, expose data or cause downtime without a replacement marker.
4. **Dependencies:** examine unknown values and deferred data reads, subnet/region changes, IP/DNS changes and propagated outputs. Unknown is uncertainty, not evidence of a benign value. Do not infer all runtime dependencies solely from Terraform's graph.
5. **Operational effect:** check rollout order, availability during transitions, provider-specific service behavior and recovery path. `prevent_destroy` is not a backup and cannot protect a resource whose configuration has been removed.
6. **Cost:** compare before/after resource shape, quantity, storage, egress and retention using dated prices for the actual region and assumptions. Identify estimates separately from measured bills; do not invent prices for unknown sizes.

Do not approve by resource count alone. A single access-policy update can matter more than hundreds of harmless metadata changes. Separate unrelated drift from the requested diff by comparing configuration, saved state and scoped live evidence; do not mutate state or apply changes merely to remove the difference.

## Findings and handoff

- Report address, planned action, concrete consequence, evidence and a proposed correction or verification. Prioritize unexplained destructive changes, target mismatch and exposure over formatting.
- Include reviewed scope, plan provenance, unknown/deferred items, policy results, runtime checks and recovery prerequisites. State when a restricted value was not inspected.
- The reviewed saved plan must correspond to the approved commit, inputs and state. Regenerate and review after relevant code, input or infrastructure changes; do not carry an old summary over to a new artifact.
- Put fixes in the owning repository. Apply and state operations follow the project's existing authority and workflow and the execution boundary above. A clean plan or successful validation does not replace explicit human approval for destructive or disruptive execution.
