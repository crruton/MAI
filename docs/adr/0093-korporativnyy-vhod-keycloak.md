# 0093. Корпоративный режим: обязательный вход через Keycloak и продление сессии

- **Статус:** accepted
- **Дата:** 2026-11-23
- **Контекст:** бэклог F21 (BACKLOG п.8), решение D1, матрица прав Q2 (ADR 0028)

## Контекст

По D1 локальная роль admin/guest — режим интерфейса, а настоящие права — только
при входе через Keycloak. Но вход был необязательным: без него приложение
работало как локальный admin, выход из Keycloak возвращал локального admin, а
access token никогда не продлевался (refresh не было вовсе) — сессия жила, пока
жив файл `auth.json`.

## Решение

- Корпоративный режим включает **организация** в `managed-settings.json`:
  `{"auth": {"required": true, "issuer": "…/realms/mai", "clientId": "mai-code-desktop"}}`.
  Пользователь и проект его не отменяют (уровни ADR 0038).
- Без действующей сессии роль — `none`: гейт `guardIpc` (`sessionGate`) пропускает
  только каналы экрана входа (`auth:status`, `auth:login`, `auth:logout`,
  `app:clipboard`, `app:focusMain`); остальное — отказ `needsLogin`. Порядок
  проверок: сессия → роль → схема данных.
- Окно в этом режиме показывает экран «только вход» до любых других вызовов:
  «Войти через Keycloak», причина неудачи и «Повторить вход»; после входа —
  перезагрузка. Раз в минуту окно проверяет сессию и при истечении снова
  показывает экран входа.
- Локальной роли нет (`auth:setRole` — отказ), адрес Keycloak не меняется из
  окна, «Выйти» ведёт на экран входа (и закрывает сессию на сервере по
  `refresh_token`), а не в локального admin.
- Продление (`auth-session.js`, без Electron): токены хранятся с отметкой
  времени; `tokenState` — valid / refreshable (access истёк или истекает за 30 с,
  refresh жив) / expired. `ensureSession` раз в минуту и при запросе статуса
  обновляет access token по `refresh_token` и пересчитывает роль из нового токена
  (роль, отнятая в Keycloak, отнимается и здесь). Отзыв или истечение refresh —
  сессия закрыта; недоступный Keycloak (сеть, 5xx) — сессия остаётся до
  следующей попытки.
- Без блока `auth` в файле организации — прежний локальный режим (D1), но
  сессия Keycloak теперь тоже продлевается и истекает.

## Альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| Флажок «обязательный вход» в настройках пользователя | Проще | Пользователь сам его снимет | Только файл организации |
| Проверять подпись JWT локально (JWKS) | Защита от подделки токена в файле | Токен и так зашифрован safeStorage; роль пересчитывается при refresh | Отложено до серверного режима |
| Блокировать при недоступном Keycloak | Строже | Сбой сети останавливает работу всех | Сессия живёт до срока refresh |

## Последствия

- В корпоративном режиме права admin/guest становятся границей для окна: без
  входа агент и настройки недоступны. От владельца машины, который правит
  файлы ОС, это по-прежнему не защищает (D1) — для этого нужен серверный режим.
- Проверки: `test-auth-session` — политика, сроки токенов, refresh, роли, матрица
  IPC с гейтом (без входа / guest / admin / без режима); `test-auth-electron` —
  поддельный Keycloak: вход с PKCE, refresh с пересчётом роли, 503, отзыв,
  выход с logout на сервере; `test-ui` [55] — экран «только вход», «Повторить
  вход», обычное окно после входа.
