# 0055. Фоновые команды

- **Статус:** accepted
- **Дата:** 2026-11-21
- **Контекст:** бэклог CC1.4

## Контекст

`run_shell` ждал конца команды (до 180 с). Сервер разработки, `watch`-сборку
или долгий тест агент запустить и проверить не мог: вызов висел до таймаута.

## Решение

- `run_shell({ command, background: true })` — процесс запускается и сразу
  возвращается id (`bg1`, …). Разрешение — как у обычной команды (класс
  `exec`, те же правила, guardrails и песочница Docker, ADR 0040); в запросе
  видно «(в фоне)».
- `shell_output({ id, all? })` — новый вывод с прошлого чтения и состояние
  («работает N с» / «завершена с кодом»); без id — список. `shell_kill({ id })`
  — остановить с дочерними процессами (`taskkill /T` / группа процессов /
  `docker kill`). Оба — класс `read`: читают и останавливают только свои
  фоновые команды.
- Вывод — кольцевой буфер 1 МБ на команду; длинный ответ уходит в файл
  (ADR 0054). Одновременно — не больше 5 команд.
- Фоновые команды живут, пока открыто приложение, и переживают ход агента
  (можно проверить сервер в следующем сообщении); при выходе из приложения
  останавливаются все.
- Общий запуск процесса вынесен в `spawnCommand` — одинаково для обычных и
  фоновых команд.

## Альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| `&` / `start` в команде | Ничего делать не надо | Процесс без присмотра: вывод потерян, не остановить, переживёт приложение | Свой реестр с выводом и остановкой |
| Останавливать в конце ответа агента | Меньше висящих процессов | Сервер разработки нужен и в следующем сообщении | Живут до выхода из приложения |

## Последствия

- Фоновые команды не видны в окне отдельной панелью — только через агента
  (`shell_output` без id); панель — следующий шаг.
- Проверки: `scripts/test-background.mjs` (14: запуск, только новый вывод,
  весь буфер, список, остановка, завершение с кодом, лимит, остановка всех,
  песочница без Docker), в CI на Linux и Windows.
