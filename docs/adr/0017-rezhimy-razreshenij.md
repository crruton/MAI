# 0017. Режимы разрешений: авто, вручную, принимать правки, план

- **Статус:** accepted
- **Дата:** 2026-11-05
- **Контекст:** запрос на режимы как в Claude Code

## Контекст

До этого решения было два состояния: подтверждать всё или включить
`autoApproveShell`. Промежуточных вариантов не было:

- нельзя было разрешить правки файлов, но оставить подтверждение команд;
- нельзя было попросить агента сначала показать план, а не менять код;
- `autoApproveShell` не покрывал запись файлов, поэтому «тихий» режим
  приходилось собирать из двух настроек.

Пользователю нужен один переключатель рядом с полем ввода, как в Claude Code.

## Решение

Введён режим разрешений. Значение хранится **в сессии** (`session.permissionMode`),
а `settings.permissionMode` служит значением по умолчанию для новых чатов.
Значения: `auto`, `manual`, `acceptEdits`, `plan`. По умолчанию `manual`.

Пустая строка в сессии означает «взять значение из настроек». Так старые
сессии, созданные до этого решения, продолжают работать без миграции.

Модуль `electron/lib/permissions.js` — единственное место, где записано
поведение режимов. Он отдаёт три вещи:

1. `decide({ mode, tool })` — судьба запроса: `allow`, `ask` или `deny` с
   причиной.
2. `hiddenToolsForMode(mode)` — какие инструменты не показывать модели.
3. `modePrompt(mode)` — абзац системного промпта под режим.

| Режим | Запись файлов | Команды оболочки | MCP и плагины |
|---|---|---|---|
| `auto` | без вопроса | без вопроса | без вопроса |
| `manual` | спросить | спросить | спросить |
| `acceptEdits` | без вопроса | спросить | спросить |
| `plan` | запрет | запрет | запрет |

Чтение (`read_file`, `list_files`, `grep`, `load_skill`) не спрашивают ни в
одном режиме: оно не меняет состояние.

В режиме `plan` инструменты записи и оболочки не передаются модели вовсе.
Это дешевле, чем отказ на каждом вызове: модель не тратит итерации на
попытки, которые всё равно запрещены.

Guardrails проверяются раньше режима и работают во всех режимах. Режим `auto`
не отключает защиту от разрушительных команд и доступа к секретам.

Режим читается на каждый вызов `approve`: сначала из сессии, затем из
настроек. Переключение в интерфейсе действует сразу, без перезапуска.

Режим принадлежит чату, а не приложению. В одном чате можно работать в
режиме «План», а в другом — в «Авто». Выбор в новом чате до первого сообщения
запоминается как значение по умолчанию и переносится в создаваемую сессию.

## Альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| Оставить `autoApproveShell` | Ничего не менять | Нет плана, нет разделения правок и команд | Не решает задачу |
| Спрашивать модель о режиме | Гибко | Непредсказуемо, тратит токены | Решение должно быть за человеком |
| Один переключатель в настройках | Просто, предсказуемо | Один режим на всё приложение | Не хватает гибкости |
| Режим в каждой сессии | Разные режимы для разных чатов | Нужно хранить и синхронизировать | **Выбран** |

## Последствия

- Проще: один селектор рядом с полем ввода; понятная таблица поведения;
  режим «План» даёт план с альтернативами до правок.
- Сложнее: `approve` теперь возвращает `true` или строку с причиной отказа.
  Все инструменты обязаны сравнивать строго `allowed !== true`. Нестрогая
  проверка `if (!allowed)` пропускает отказ, потому что непустая строка
  истинна. Это исправлено в `write_file`, `edit_file` и `run_shell`.
- Проверить: `npm.cmd test` — 55 проверок режимов, 24 интеграционных, 35
  проверок вложений и 4 проверки оболочки. `npm.cmd run test:electron` — 25
  проверок в настоящем Electron, включая независимость режимов двух сессий.
  Приложение запускается и держит окно. Ручной прогон сценариев в интерфейсе
  (переключение режима, модальное подтверждение) не выполнялся.
- Риск: пользователь включит `auto` и не заметит. Снижение — цвет селектора
  и подсказка при переключении.
