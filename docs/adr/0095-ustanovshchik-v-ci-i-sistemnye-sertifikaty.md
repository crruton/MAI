# 0095. Установщик в CI на чистом Windows и системные сертификаты в процессе

- **Статус:** accepted
- **Дата:** 2026-11-23
- **Контекст:** бэклог F25 (ROADMAP «проверка EXE на чистой машине»), ADR про сертификаты в ARCHITECTURE

## Контекст

EXE собирался только по тегу и ни разу не запускался после установки: что
asar содержит всё нужное, что приложение живёт без Node.js на машине и что
удаление чистое — не проверялось. Первая же самопроверка собранного приложения
нашла дефект: в упакованном Electron `NODE_OPTIONS` игнорируется, и перезапуск
с `--use-system-ca` не включал системные корневые сертификаты. Установленный EXE
не доверял корпоративному корню Windows — запросы к шлюзу MAI падали бы с
«unable to get local issuer certificate», хотя из исходников всё работало.

## Решение

- `system-ca.js` — `applySystemCa()`: встроенные + системные корни через
  `tls.setDefaultCACertificates([...getCACertificates('default'), ...('system')])`
  прямо в main при старте; действует на `https`, `fetch` (SDK OpenAI) и всё, что
  идёт через `tls`. Перезапуск с `NODE_OPTIONS` остался запасным путём, только
  если API нет (старый Electron). CLI и окно больше не перезапускаются.
- `self-check.js` — `MAI Code.exe --self-check[=отчёт.json]`: без окна проверяет
  файлы внутри asar (окно, preload, документация), встроенные навыки, модули
  main (`openai`, `pdf-lib`, MCP SDK) и упакованный `mermaid`, запись в папку
  данных, `cmd.exe`, встроенный Node.js, DPAPI (на Windows обязателен) и
  системные корни; отчёт — JSON, код выхода 0/1.
- `scripts/check-installer.ps1` — на чистом раннере: тихая установка NSIS
  (`/S /D=`), файлы и ярлыки, самопроверка установленного и portable-EXE с PATH
  **без Node.js**, тихое удаление (файлы и ярлыки исчезают).
- CI: задача `installer` на `windows-latest` при каждом push и PR — сборка,
  проверка, `SHA256SUMS.txt`, артефакт на 7 дней. Релиз по тегу запускает ту же
  проверку перед публикацией.
- Подписи нет: сертификат подписи — секрет организации; electron-builder
  подпишет сам, если в секретах задать `CSC_LINK` и `CSC_KEY_PASSWORD` (в CI
  сейчас `CSC_IDENTITY_AUTO_DISCOVERY=false`).

## Альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| Флаг `--use-system-ca` в fuses/командной строке Electron | Без кода | Это флаг Node, не Chromium; в packaged NODE_OPTIONS закрыт | API `tls` в процессе |
| Проверка установщика только при релизе | Быстрее CI | Дефект виден в день релиза | Каждый push |
| Windows Sandbox / VM с нуля | Чище раннера | Нет в GitHub Actions | Раннер без Node в PATH процесса |

## Последствия

- Корпоративный корень работает и в установленном EXE, а старт быстрее — без
  перезапуска процесса.
- CI дольше примерно на сборку NSIS (несколько минут) и хранит EXE 7 дней.
- Раннер — не совсем «чистая машина»: Node.js там установлен, но из PATH
  проверяемого процесса убран; Visual C++ и .NET на раннере есть всегда.
- Проверки: `test-self-check` — аргументы, проверка исходников, сломанная
  установка (нет файлов, модуля, DPAPI, сертификатов), `applySystemCa`;
  собранное Linux-приложение прошло `--self-check` без Node.js в PATH; Windows —
  задача `installer` в CI.
