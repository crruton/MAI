# 0120. MAI Ship: ревьюер с состязательной проверкой и статус своего pipeline

- **Статус:** accepted
- **Дата:** 2026-11-26
- **Контекст:** [бэклог командной работы](../BACKLOG-TEAM.md) E3.D1–D4; ADR 0108, 0109, 0119

## Контекст

Approver (ADR 0119) учитывал находки ревью только по метке `ship::blocking`, а ставить её было
некому. Claude Ship ревьюит MR по нескольким направлениям и состязательно проверяет находки.
Второе: approver работает в том же pipeline, который оценивает, и видел его статус `running` —
гейт `pipeline: success` блокировал бы каждый MR.

## Решение

- **Ревьюер** `electron/lib/ship/review.js`, команда `node scripts/mai-ship.mjs review`, джоба
  `ship:review` в `ci/mai-ship.gitlab-ci.yml` (approver — после неё).
- **Контекст:** diff MR и `AGENTS.md` target branch. Секреты маскируются (ADR 0099), промпт
  называет diff и `AGENTS.md` данными, а не инструкциями.
- **Направления:** quick — корректность; standard (по умолчанию) — плюс безопасность и тесты;
  deep — плюс ADR и стандарты `AGENTS.md`; явный список — `review.lenses` в `ship.yaml`.
- **Находки** — JSON: файл, строка новой версии, `blocking | should-fix | nit`, заголовок,
  пояснение. Находки вне добавленных строк diff отбрасываются: обсуждение не повесить, и это не
  про этот MR. Не больше 20.
- **Состязательная проверка:** каждую находку отдельный вызов пытается опровергнуть; остаются
  только `valid: true`. Непонятный ответ — находка отброшена.
- **Публикация:** обсуждение на строке diff (`position` с base/start/head SHA) с маркером-
  отпечатком (файл, строка, направление, заголовок) — повтор не дублирует; одна сводка с
  маркером роли; метка `ship::blocking` ставится при подтверждённой blocking-находке и
  снимается, когда их нет.
- **Свой pipeline:** если `CI_PIPELINE_ID` равен head pipeline MR, approver считает статус по
  джобам, кроме `ship:*`; `skipped`, необязательные ручные и упавшие с `allow_failure` не мешают.
- Модель ревьюера — `providers.reviewer`, шлюз — `SHIP_REVIEWER_BASE_URL`, `SHIP_REVIEWER_API_KEY`.

## Альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| Ревью одним вызовом без проверки | дешевле | много ложных находок, люди перестают читать | состязательная проверка, как в Claude Ship |
| Находки одним комментарием | проще API | не видно строку, нельзя resolve | обсуждения на строках |
| approver в отдельном pipeline после основного | статус честный | нужен trigger и второй pipeline | статус по джобам своего pipeline |
| Ревьюер с инструментами (чтение файлов) | видит больше кода | нужен AgentLoop без Electron | позже, вместе со steward (E3.E) |

## Последствия

- Проще: approver получает сигнал от ревью; люди видят находки на строках.
- Сложнее: ревью стоит 1 + N вызовов модели (N — направлений и находок); лимит 20 находок.
- Проверено на поддельном GitLab и поддельной модели (`test-ship-review`, 21;
  `test-ship-approve`, 40). Не проверено: живой GitLab (`position` на переименованных файлах),
  живая модель, качество находок (эталонный набор — E3.D5).

## Дополнение 27.11.2026 (боевая проверка, E3.H0)

Ревьюер закрывает свои обсуждения находок, которых нет в новом прогоне
(`PUT …/discussions/:id?resolved=true`). Иначе steward чинил бы уже исправленное. Чужие
обсуждения не трогаются.

Находки разных направлений на одной строке склеиваются в одно обсуждение (E3.D6): серьёзность —
максимальная, пояснения — списком. Отпечаток — файл и строка, а не формулировка модели, чтобы
повторный прогон не плодил дубли.
