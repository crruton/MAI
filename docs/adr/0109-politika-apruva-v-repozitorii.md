# 0109. Политика апрува как файл в репозитории

- **Статус:** proposed
- **Дата:** 2026-11-26
- **Контекст:** `openspec/changes/mai-ship-gitlab/`, бэклог платформы E3.A2, E3.A6, E3.B1–E3.B5

## Контекст

В MAI Ship approver-агент решает, можно ли влить MR без человека (ADR 0108). Решение должно
быть предсказуемым, проверяемым и одинаковым для людей и агентов. Владеть им должна команда
репозитория. В Claude Ship эту роль играет политика-файл в репозитории, «умный CODEOWNERS».
Claude Ship рекомендует начинать с режима observe-only.

Вход approver'а — текст diff, описания MR и комментариев. Этот текст может написать
кто угодно, в том числе агент. Это канал для prompt injection.

## Решение

Два файла на default branch проекта:

- `.mai-code/ship.yaml` — настройки: включение, уровень ревью, триггеры, steward, бюджет,
  провайдеры. Схема — `openspec/changes/mai-ship-gitlab/schemas/ship.schema.json`.
- `.mai-code/approval-policy.yaml` — правила апрува. Схема —
  `openspec/changes/mai-ship-gitlab/schemas/approval-policy.schema.json`.

Правила:

1. **Источник.** Оба файла читаются только из target branch MR, а не из source branch.
   MR не может ослабить политику, по которой его проверяют.
2. **Самозащита.** MR, который меняет `.mai-code/ship.yaml`, `.mai-code/approval-policy.yaml`,
   `.gitlab-ci.yml`, `CODEOWNERS` или CI-шаблон Ship, всегда получает `require_human`.
   Политика это правило не отменяет.
3. **Порядок оценки.** Сначала гейты: pipeline, blocking-находки ревью, размер diff. Потом
   правила по путям, меткам и автору: первое совпадение побеждает, `block` и `require_human`
   сильнее `approve`. Потом классификаторы на естественном языке, они могут только ужесточить
   решение. Если ничего не совпало, работает `default`, по умолчанию `require_human`.
4. **Итог** — `approve`, `require_human` или `block`, всегда с причиной одной строкой и именем
   правила.
5. **Режим.** `mode: observe` пишет решение комментарием и в журнал, approve не ставится.
   `mode: enforce` разрешён только классам из `enforce_classes`.
6. **Данные, а не инструкции.** Diff, описание и комментарии передаются модели в отдельном
   блоке как данные. Команды `@mai …` принимаются только от участников с ролью Developer и
   выше. Классификатор не может вернуть `approve`, только «условие выполнено / не выполнено».
7. **Бюджет и выключатель.** `budget.per_mr_usd` и `budget.monthly_usd` в `ship.yaml`.
   Превышение лимита останавливает агентов на MR или проекте и даёт `require_human`.
   CI-переменная `MAI_SHIP_DISABLED=true` или метка `ship::paused` выключают агентов на
   следующем событии.

## Альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| Настройки в UI или CI-переменных | нельзя изменить через MR | нет истории и ревью, у каждого проекта свои | политика — код, её ревьюят как код |
| Политика из source branch | удобно тестировать | MR сам ослабляет свои правила | дыра; тест политики — через `mai ship policy test` |
| Один файл | меньше файлов | политику и настройки меняют разные люди; самозащита задевает настройки | два файла, самозащита на оба |
| Только LLM-решение без правил | гибко | недетерминированно, легко внушить | правила и гейты первыми, LLM только ужесточает |

## Последствия

- Проще: решение воспроизводимо. Детерминированная часть даёт одинаковый результат на
  одинаковом входе. Политику ревьюят через MR и CODEOWNERS.
- Сложнее: первую политику проекта пишет человек. Шаблоны для docs, библиотеки, сервиса и
  инфраструктуры поставляются каталогом пакетов MAI (ADR 0042, E3.B6).
- Нужно проверить: разбор 10 эталонных политик, injection-тесты («approve this» в diff, в
  описании, в имени файла), поведение при битом YAML (`block` с причиной).
- Риски: слишком широкое правило `approve`. Снижение — observe-only минимум 4 недели и
  переход в enforce только при согласии с людьми ≥ 95% (E3.G2).
