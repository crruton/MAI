# 0062. Доски и артефакты без потери правок

- **Статус:** accepted
- **Дата:** 2026-11-22
- **Контекст:** бэклог F9, F11

## Контекст

- Доски — один `boards.json`, который пишут несколько окон (доска поставки,
  архитектуры, раннеры): окно со старой копией перезаписывало правки другого.
- Хранилище артефактов — `index.json` и блобы: без блокировки два процесса
  теряли записи друг друга, блобы удалённых артефактов копились навсегда
  (отмечено в ROADMAP).

## Решение

- **Доски.** Запись атомарная (временный файл и `rename`). У каждой секции
  (`delivery`, `architecture`, `runners`, `quality`) — номер версии в `revs`,
  растёт только у изменившейся секции. Окно сохраняет секцию с версией, которую
  видело (`boards:save({ section, data, rev })`); другое окно успело сохранить
  её — ответ `conflict` со свежими данными: окно показывает их и просит
  повторить правку. Правки разных секций не конфликтуют. Вызов без `rev` —
  как раньше.
- **Артефакты.** Изменение индекса — под блокировкой `index.lock`
  (`electron/lib/file-lock.js`: атомарное создание файла, ожидание до 5 с,
  зависшая блокировка старше 30 с снимается, повторный вход в процессе без
  ожидания); индекс пишется атомарно. `gcBlobs` удаляет блобы, на которые не
  ссылается ни одна версия; запускается после удаления артефакта.

## Альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| SQLite | Транзакции из коробки | Нативный модуль, сборка под каждую ОС | JSON + блокировка достаточно для объёма досок |
| Слияние правок вместо конфликта | Меньше повторов | Неочевидный результат при правке одной задачи | Явный конфликт с актуальной версией |

## Последствия

- При конфликте правка в окне теряется — её нужно повторить (окно уже
  показывает чужие изменения).
- Проверки: `scripts/test-storage-safety.mjs` (14: версии секций, конфликт,
  разные секции, атомарность, GC, зависшая блокировка, два процесса
  инкрементируют счётчик под блокировкой без потерь), в CI на Linux и Windows.

## Дополнение (22.11.2026): Windows

На Windows файл блокировки, который другой процесс как раз удаляет, и замена
файла, открытого на чтение, дают `EPERM`/`EACCES`/`EBUSY`, а не `EEXIST`.
`withFileLock` считает эти коды «занято» и ждёт; удаление блокировки — с
повторами; атомарная замена индекса артефактов и досок — `renameWithRetry`
(до ~1 с повторов). Найдено падением `test-storage-safety` [3] на Windows CI.
