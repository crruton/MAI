# 0019. Лимиты памяти для локальных Docker-стеков

- **Статус:** accepted
- **Дата:** 2026-11-08
- **Контекст:** жалоба «Docker съедает всю память» на локальной машине

## Контекст

На проверочной машине одновременно работают пять независимых стеков Docker:

| Стек | Файл | Контейнеров |
|---|---|---|
| Приложение (Postgres, Vault, SeaweedFS) | `infra/docker-compose.yml` | 3 |
| Keycloak + Postgres | `infra/keycloak/docker-compose.yml` | 2 |
| Multica (Postgres, backend, web) | `infra/multica/docker-compose.yml` | 3 |
| Observability (8 сервисов) | `infra/observability/docker-compose.yml` | 8 |
| k3d-кластер | создаётся вручную | 1+ |

Замер `node scripts/docker-mem.mjs` на этой машине: **18 запущенных
контейнеров, суммарно 536 МБ**. Ни у одного контейнера не было лимита памяти
(`HostConfig.Memory = 0`).

Отсюда два разных вывода, и их нельзя путать:

1. Сами контейнеры занимают немного. 536 МБ не объясняют нехватку памяти.
2. Отсутствие лимита означает, что **потолка нет**: при нагрузке (сборка,
   индексация, JVM Keycloak, Phoenix) любой контейнер может вырасти до размера
   всей доступной памяти хоста.

Основной потребитель памяти на Windows — виртуальная машина WSL2, в которой
работает Docker Desktop. Её размер задаётся в `%USERPROFILE%\.wslconfig`.

**Известный факт из практики:** попытка ограничить WSL2 уже приводила к тому,
что Docker переставал запускаться, и лимиты пришлось поднять обратно. Причина
типовая: лимит ВМ оказался меньше суммы `mem_limit` контейнеров, которые
запускаются одновременно. Демон стартует, но контейнеры падают по OOM, а
`dockerd` может не получить память на собственные нужды.

## Решение

1. **Лимиты в compose — основная защита.** В каждый сервис четырёх
   compose-файлов добавлены `mem_limit`, `cpus`, `pids_limit` и общий якорь
   `x-logging` с ротацией логов (`max-size: 10m`, `max-file: 3`).

   | Сервис | `mem_limit` | `cpus` |
   |---|---|---|
   | Postgres (все стеки) | 512m | 1.0 |
   | Vault | 256m | 0.5 |
   | SeaweedFS | 512m | 1.0 |
   | Keycloak | 1g | 1.0 |
   | Multica backend | 512m | 1.0 |
   | Multica web | 256m | 0.5 |
   | Loki, Tempo, Prometheus | 512m | 1.0 |
   | OTel Collector | 256m | 0.5 |
   | Grafana | 384m | 0.5 |
   | Phoenix | 1g | 1.0 |
   | Phoenix DB | 256m | 0.5 |

   Сумма лимитов по стекам:

   | Стек | Сумма `mem_limit` |
   |---|---|
   | Приложение | 1,25 ГБ |
   | Keycloak | 1,25 ГБ |
   | Multica | 1,25 ГБ |
   | Observability | 4,0 ГБ |
   | **Все четыре сразу** | **7,75 ГБ** |

2. **Keycloak и JVM.** Добавлен `JAVA_OPTS_APPEND: -XX:MaxRAMPercentage=70
   -XX:+UseSerialGC`. Без этого JVM ориентируется на память хоста, а не
   контейнера, и резервирует heap под весь хост.

3. **Ротация логов.** `json-file` без ограничения растёт без предела и на
   Windows учитывается в памяти WSL2. Ограничение — 10 МБ × 3 файла на сервис.

4. **Диагностика.** `scripts/docker-mem.mjs` (`npm run docker:mem`) показывает
   фактическое потребление, лимит, сумму лимитов и запас до лимита ВМ.
   `npm run docker:mem:check` возвращает код 1, если найден контейнер без
   лимита или если сумма лимитов превышает память, доступную демону.

5. **Правило для `.wslconfig`.** Лимит ВМ задаётся **не меньше** суммы
   `mem_limit` одновременно работающих стеков плюс запас на сам Docker Desktop
   (≈1 ГБ) и k3d (≈2 ГБ), если он нужен. Пример для 16 ГБ RAM и двух стеков:

   ```ini
   [wsl2]
   memory=8GB
   processors=4
   swap=4GB
   ```

   Меньшее значение допустимо только при остановленных стеках. Порядок
   применения: изменить `.wslconfig` → `wsl --shutdown` → запустить Docker
   Desktop → `docker info` → `npm run docker:mem:check`.

6. **Остановка неиспользуемых стеков.** Стеки независимы. Держать все пять
   одновременно не нужно: `npm run obs:down`, `npm run infra:down`,
   `docker compose -f infra/keycloak/docker-compose.yml down`.

## Альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| Только `.wslconfig` | Одно место, лечит корень на Windows | Не ограничивает отдельный контейнер, ломает Docker при малом значении | Нужен вместе с лимитами, а не вместо |
| Только лимиты в compose | Кроссплатформенно, в репозитории, безопасно | Не ограничивает саму ВМ WSL2 | Выбран как основной |
| `docker system prune` | Освобождает диск | Не влияет на RAM | Другая задача, уже есть `docker:gc` |
| Один общий compose на все стеки | Меньше файлов | Нельзя поднять часть, ломает независимость слоёв | Нарушает `docs/DEPLOYMENT.md` |

## Последствия

- Проще: у каждого сервиса есть потолок, `docker:mem:check` ловит регрессию.
- Сложнее: при нехватке памяти контейнер будет убит по OOM, а не «съест» хост.
  Значения лимитов придётся поднимать точечно.
- Проверено: `docker compose config --quiet` для всех четырёх файлов.
- Не проверено: живой прогон с новыми лимитами. Контейнеры запущены со старой
  конфигурацией, для применения нужен `up -d`.
- Не проверено: содержимое `.wslconfig` и размер `vmmem` на машине — команды
  чтения не были подтверждены.
- Риск: `mem_limit` ниже реальной потребности даст OOM-kill. Смягчение —
  значения взяты с запасом ×4 от измеренных 536 МБ на 18 контейнеров.
- Риск: слишком малый лимит WSL2 останавливает Docker. Смягчение — правило из
  пункта 5 и проверка `docker:mem:check` перед изменением `.wslconfig`.
