# 0003. OpenSpec как вход, Multica как доска

- **Статус:** accepted
- **Дата:** 2026-11-04

## Контекст

Задачи обсуждаются в чате и теряются. Нужен предсказуемый формат: сначала
спецификация изменения, потом задачи, потом код. Multica умеет хранить задачи,
но не заменяет спецификацию.

## Решение

Двухступенчатый процесс:

1. **OpenSpec** — изменение описывается в `openspec/changes/<name>/`:
   `proposal.md`, `specs/`, `design.md`, `tasks.md`.
2. **Multica** — задачи из `tasks.md` синхронизируются в workspace через REST
   API или CLI. Каждая задача содержит ссылку на изменение OpenSpec.

Формулировки задач — по ASD-STE100: короткие предложения, активный залог,
одна инструкция на предложение, без идиом. Шаблон — `skills/openspec-multica`.

Синхронизация идемпотентна: ключ — `openspec:<change>:<task-id>`. Повторный
запуск обновляет задачу, а не создаёт дубль.

## Альтернативы

| Вариант | Плюсы | Минусы |
|---|---|---|
| Только Multica | Одна система | Нет спецификации и дизайна |
| Только OpenSpec | Полный контекст | Нет статусов и исполнителей |
| Две системы + sync | Контекст и учёт | Нужна синхронизация |

## Последствия

- Без настроенного Multica приложение работает: sync возвращает понятную ошибку.
- Локальная Multica поднимается через `infra/multica/docker-compose.yml`.
- API-токен хранится в настройках, не в git.
- Ограничение: Multica API может меняться; клиент изолирован в
  `electron/lib/multica.js`.
