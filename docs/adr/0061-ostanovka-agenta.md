# 0061. Остановка агента: прерываемые инструменты и сторож простоя

- **Статус:** accepted
- **Дата:** 2026-11-22
- **Контекст:** жалоба «агент зависает и не реагирует на Стоп»

## Контекст

Кнопка «Стоп» в интерфейсе вызывала `chat:stop`, тот делал
`state.controller.abort()`. Дальше ничего не происходило. Причин было четыре,
и каждая давала свой симптом.

| Симптом | Причина |
|---|---|
| «Стоп» не работает | `execute()` в `electron/lib/tools/shell.js` не принимал `signal`; команда жила до таймаута 180 с (исправлено в 0.2.0) |
| «Стоп» не работает для MCP | `withTimeout()` в `electron/lib/mcp.js` не учитывал сигнал и ждал 120 с; `mcp.call()` не получал сигнал |
| «Зависает» | нет контроля простоя хода модели: если шлюз принимал соединение и молчал, `for await` по стриму ждал бесконечно |
| «Не реагирует» | `state.controller` не освобождался, если прогон завис; следующий запрос получал «Уже выполняется другой запрос» навсегда |

Дополнительно: `child.kill()` на Windows завершает только `cmd.exe`. Сама
команда (`npm`, `python`, `docker`) остаётся жить и держит пайп открытым,
поэтому промис инструмента не резолвится даже после `kill()`.

## Решение

Сигнал остановки проходит через все слои, а простой ограничен по времени.

1. **`execute(command, cwd, { signal })`** — принимает сигнал. По abort
   вызывает `killTree()`: на Windows `taskkill /pid <pid> /T /F`, иначе
   `SIGTERM`. Уже отменённый сигнал не запускает команду вовсе. В 0.2.0
   это дополнено песочницей (`docker kill`) и фоновыми командами.
2. **`withTimeout(promise, ms, message, signal)`** — добавляет в `Promise.race`
   гонщика, который рвётся по abort. Слушатель снимается в `finally`.
   `McpManager.call(toolName, args, signal)` передаёт сигнал из контекста
   инструмента: `run: (ctx, args) => mcp.call(name, args, ctx?.signal)`.
3. **`idleGuard(signal, ms, onIdle)`** в `electron/lib/agent.js` — сторож на
   один ход модели. Даёт собственный `AbortController`, сбрасывается на каждом
   чанке (`touch()`), по тишине 120 с прерывает ход. Флаг `timedOut()`
   отличает простой от остановки пользователем, чтобы не переключиться на
   `/v1/responses` по ошибке обрыва.
4. **`chat:stop`** — после `abort()` ставит таймер `STOP_GRACE_MS = 5000`.
   Если прогон не завершился, состояние освобождается принудительно и UI
   получает событие `error` с `aborted: true`.
5. **`streamResponseTurn({ touch })`** — транспорт `/v1/responses` зовёт
   `touch()` на каждом событии стрима, поэтому сторож видит жизнь и не
   рвёт долгий, но живой ответ.

Контекст инструментов получил поле `signal`, поэтому `run_shell` передаёт его
в `execute`, а `mcp.call(name, args, signal)` — в `withTimeout`.

## Альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| Только `child.kill()` | одна строка | на Windows дочерние процессы выживают, пайп не закрывается | не решает проблему |
| Убивать процесс по PID без `/T` | проще | `npm` оставляет `node`-потомков | тот же дефект |
| Жёсткий таймаут на весь ход | просто | рвёт долгую легитимную работу (сборка, тесты) | сторож простоя точнее: считает тишину, а не общее время |
| Перезапуск окна при зависании | не требует кода | теряется контекст сессии | недопустимо |

## Последствия

- Проще: «Стоп» действует на команды, MCP и молчащий шлюз; зависший прогон
  больше не блокирует следующие запросы.
- Сложнее: `execute` и `withTimeout` получили дополнительный параметр; вызовы
  без сигнала работают как раньше.
- Проверить: `npm.cmd test` — блок `[3]` в `scripts/test-shell.mjs`
  (живой вывод и «Стоп»), `scripts/test-agent-loop.mjs` (цикл агента).
- Риск: `taskkill /T` убивает дерево процессов целиком, включая фоновые
  серверы, запущенные той же командой. Это ожидаемо для «Стоп», но не для
  таймаута — таймаут тоже использует `killTree`, и это осознанно: иначе
  процесс остаётся сиротой.
