## 0. Коротко

1. **Хранилище скиллов — это каталог пакетов MAI** (ADR 0037, 0042), а не новый сервис.
   MAI уже ставит пакеты из git-каталога `mai-marketplace.json` и обновляет их по semver.
   Не хватает трёх вещей: каталога команды с отобранными скиллами, отдачи скиллов в
   Multica MAI и экспорта в Claude Code и OpenCode.
2. **73 входных скилла (`multica-skills-full`) нельзя положить в MAI как есть.** Репозиторий
   публичный (AGENTS.md, п. 10). В 24 файлах прописаны внутренние хосты, в `people.yaml`
   лежат email сотрудников. 6 скиллов продублированы между двумя workspace. Публикацию MR
   делают 4 скилла, `prd` существует в 3 вариантах. Ни у одного скилла нет `version`, а без
   неё MAI скилл не обновляет (ADR 0101). Решение: в публичный каталог идут очищенные
   общие скиллы, организационные — в приватный каталог (ADR 0042 поддерживает приватный
   git-каталог).
3. **Команда в MAI — это общий профиль, а не общий процесс Electron.** Опора: Keycloak и
   `managed-settings.json` (ADR 0038, 0093), каталог пакетов, workspace и squads в Multica
   MAI. Серверный режим MAI для MVP не нужен.
4. **Человека в петле заменяет политика, а не «вторая нейронка сказала ок».** MAI Ship
   повторяет механику Claude Ship на примитивах GitLab: ревью, steward без права апрува,
   approver по политике-файлу, старт в observe-only. Approver — из другого семейства
   моделей, чем исполнитель (ADR 0110). Детерминированные гейты идут до модели.
5. **Маркетплейс на Authentik спорит с ADR 0093 (Keycloak).** Нужен ADR. Рекомендация:
   Authentik — шлюз витрины, Keycloak MAI — IdP, федерация OIDC. Витрина для MVP —
   встроенная страница «My applications» в Authentik.

## 1. Продуктовая проработка

### П1. Единое хранилище скиллов

- **Проблема.** Хороший скилл живёт в одном месте, а нужен везде: в чате MAI, у агентов
  Multica MAI, у коллег в Claude Code и OpenCode. Сейчас скиллы копируют руками, и копии
  расходятся.
- **Пользователи.** Автор скилла. Потребитель — агент MAI, агент Multica или разработчик в
  IDE. Владелец каталога.
- **JTBD.** «Когда я улучшил скилл, я хочу, чтобы все агенты команды получили улучшение без
  копирования, и чтобы проверки показали, что ничего не сломалось».
- **Гипотеза.** Если каталог MAI — единственный источник, а MAI сам отдаёт скиллы в Multica
  и в форматы других агентов, дублей не будет, а лаг «правка → использование» станет меньше
  дня.
- **Метрики.** Дубли (на входе 6 полных и 5 расходящихся пар). Доля скиллов с `version`,
  `owner` и сценариями eval (на входе 0%). Число потребителей каталога. Лаг публикации.
- **MVP.** Каталог `catalog/` с `mai-marketplace.json` в MAI. Наборы по ролям. Команда
  `/skills push multica` и `mai skills export --target claude|opencode|codex`.
- **Не делаем.** Сервер-реестр с поиском и статистикой: ADR 0042 отверг его в пользу git.
- **Закрываем, если** через 6 недель каталог читают меньше двух потребителей или скиллы
  по-прежнему копируют руками.

### П2. MAI для команды

- **Проблема.** MAI однопользовательский. Без Keycloak роли — режим интерфейса (D1).
  Multica-синхронизация идёт в workspace по умолчанию (`workspaceId` не передаётся).
  Настройки, навыки и память живут в `%APPDATA%` одного человека.
- **JTBD.** «Когда я прихожу в проект, я хочу за один вход получить правила, скиллы, MCP и
  задачи команды».
- **Гипотеза.** Если вход через Keycloak применяет профиль команды и выбирает workspace
  Multica, новый участник начинает работу меньше чем за 15 минут.
- **Метрики.** Время до первой задачи. Доля машин с актуальным профилем.
- **MVP.** Профиль команды — git-репозиторий (managed-settings, каталоги, MCP без секретов,
  `AGENTS.md`). Выбор workspace и проекта Multica. Атрибуция действий агента пользователю.
- **Не делаем.** Серверный MAI, совместное редактирование чата в реальном времени, свой
  бэкенд пользователей.
- **Закрываем, если** команда из 5 человек за 2 недели не получает выигрыша относительно
  Claude Code с каталогом.

### П3. MAI Ship: непрерывный цикл без человека в рутине

- **Проблема.** Агенты пишут код быстрее, чем люди апрувят. Claude Ship решает это, но
  только на GitHub. Апрув той же моделью, что писала код, ничего не проверяет.
- **JTBD.** «Когда изменение рутинное и прошло гейты, я хочу, чтобы оно вливалось без меня.
  Когда оно рискованное, я хочу узнать об этом с причиной».
- **Гипотеза.** На рутине (docs, тесты, мелкие фиксы) решение approver'а совпадает с
  решением человека в ≥ 95% случаев. Lead time MR падает в 3 раза, доля revert не растёт.
- **Метрики.** Согласие approver'а с человеком, lead time, revert за 14 дней, стоимость на
  MR, доля эскалаций.
- **MVP.** Раздел E3. Пилот — 4 недели в `mode: observe` на тестовом GitLab-проекте;
  эталон — Claude Ship на `crruton/MAI` за тот же срок.
- **Не делаем.** Автомерж мимо branch protection. Самоапрув. Бесконечные раунды.
- **Закрываем, если** согласие после калибровки ниже 90% или растёт доля revert.

### П4. Маркетплейс продуктов

- **Проблема.** Агенты в MAI делают продукты двух видов: для разработки (скиллы, пакеты, MCP,
  шаблоны) и для использования (сервисы, боты, дашборды). Первые — это каталог П1. Вторым
  негде жить с SSO, владельцем и способом снять их с публикации.
- **JTBD.** «Когда агент собрал полезное приложение, я хочу одним MR опубликовать его
  коллегам с SSO, владельцем и сроком жизни».
- **Гипотеза.** Если публикация — MR с манифестом, а Authentik сам показывает приложение в
  «My applications», путь «собрано → доступно» займёт меньше дня.
- **MVP.** `infra/authentik`, манифест приложения, пайплайн публикации, витрина Authentik.
- **Не делаем.** Свою витрину, биллинг, рейтинги, внешних пользователей.
- **Закрываем, если** за квартал опубликовано меньше 5 приложений с реальными пользователями.

## E3. MAI Ship: декомпозиция Claude Ship под GitLab (П3)

Спека: `openspec/changes/mai-ship-gitlab/`, решения — ADR 0108, 0109, 0110.
Сделано: E3.A1–A3, E3.A6, E3.B1–B3, E3.F2, проверки бюджета и выключателя в `evaluate`.

Цель — повторить механику Claude Ship на примитивах GitLab и движке MAI Code для пользователей MAI с GitLab. Claude Ship работает только с GitHub, поэтому продукт берём как образец.

### E3.0. Как Claude Ship раскладывается на GitLab

| Механизм Claude Ship | Что делает | Примитив GitLab | Компонент MAI Code |
|---|---|---|---|
| `/ship` в Claude Code | push, создание PR, ревью, работа с замечаниями и красными проверками | `git push` + `glab mr create --draft` | команда `/ship` (скилл `to-mr` + `mai -p`, ADR 0077) |
| Code Review | ревью по нескольким направлениям, состязательная проверка находок, категории, уровни Quick/Standard/Deep | MR discussions с позицией в diff (`POST /merge_requests/:iid/discussions`), метки `ship::review::*` | агент `ship-reviewer` (субагенты, ADR 0075) |
| PR Steward | держит MR зелёным: CI, конфликты, замечания; **не апрувит и не мержит**; комментарий «что изменил / как откатить»; `@claude <указание>`, `@claude stop` | Pipeline/Note/MR webhooks; push в source branch от бот-учётки; rebase API; resolve discussions | агент `ship-steward` |
| Claude Approvals | политика-файл в репозитории, «умный CODEOWNERS»; апрув рутины; обязательный человек по условиям; классификаторы на естественном языке | `POST /merge_requests/:iid/approve` с параметром `sha`; approval rules (Premium); на Free — обязательная джоба `ship-approval` и «Pipelines must succeed» | агент `ship-approver` + движок политики |
| Observe-only | approver решает, но не влияет на мерж | комментарий-решение без approve; метка `ship::observe` | флаг `mode: observe` в политике |
| Включение по репозиториям, своя глубина ревью, время запуска, лимит затрат в месяц | настройки на репозиторий | `.mai-code/ship.yaml` на default branch, CI/CD variables группы | конфиг + учёт затрат (OTel, ADR 0094) |
| Политика включается, когда файл есть на default branch; админ может выключить | действует только версия из защищённой ветки | читать файл из `target_branch`, а не из MR | движок политики |
| Совместимость с branch protection и required checks | Ship не обходит защиту | protected branches, CODEOWNERS, merge checks | не обходим; только добавляем |

Наше отличие от Ship: approver от **другого провайдера**, чем исполнитель и ревьюер. Детерминированные гейты идут до любой модели.

### E3.A. Архитектура и решения

| ID | Задача | P | Дн | Критерий приёмки | Зав. |
