Состояние: 18.11.2026, ветка `dev` (`a8e3138`). Аудит кода, а не документации:
каждый пункт ссылается на место, где поведение расходится с заявленным.

Приоритеты:

- **P0** — дыра в безопасности или фича работает не так, как обещает UI. Чинить первым.
- **P1** — паритет с диалоговым интерфейсом уровня Claude Code.
- **P2** — выравнивание остальных фич и долг.

Оценки — в идеальных днях одного разработчика.

## 0. Целевая модель (к чему выравниваемся)

Одна точка принятия решений — **PolicyEngine в main-процессе**. Через неё проходит
*каждый* вызов, который меняет состояние: встроенные инструменты, MCP, плагины,
внешние рантаймы, стадии досок, самокоррекция. Инструмент не вызывает `approve`
сам — его оборачивает агентный цикл. Тогда новый инструмент нельзя «забыть»
защитить.

```
tool_call → classify(tool, args) → guardrails → rules(allow/deny/ask) → mode → [ask UI] → run → audit log
```

- `classify` возвращает класс действия: `read`, `write`, `exec`, `network`, `external`
  (MCP/плагин без метаданных = `external`, считается опасным).
- `rules` — явные правила как в Claude Code: `allow: ["run_shell(npm test*)"]`,
  `deny: ["write_file(.github/**)"]`, уровни: сессия → проект → глобально.
- `mode` (`plan` / `manual` / `acceptEdits` / `auto`) — только политика по умолчанию
  для того, что не покрыто правилами. `deny` и guardrails сильнее любого режима.
- Решение пишется в журнал: кто, что, режим, правило, ответ пользователя.

## E1. Движок разрешений (P0)

### E1.1 MCP-инструменты выполняются без проверки — P0, 1 д
`electron/lib/agent.js:290` вызывает `mcp.call()` напрямую: `approve` не вызывается,
режим «План» их не скрывает (`hiddenToolsForMode` скрывает только запись и shell).
В «Плане» и «Вручную» агент может вызвать MCP-инструмент файловой системы и
записать файл без вопроса.
**Сделать:** вызов MCP — через PolicyEngine, класс `external`; читать аннотации
MCP `readOnlyHint` / `destructiveHint`, без них — `ask`. В «Плане» показывать только
MCP-инструменты с `readOnlyHint: true`.
**Приёмка:** интеграционный тест: фейковый MCP-сервер с `write`, режимы plan/manual
не пишут без подтверждения.

### E1.2 Плагины решают сами, спрашивать ли — P0, 1 д
`tool.run({ approve, ... })` (`agent.js:294`) — плагин может не вызвать `approve`.
**Сделать:** плагин объявляет `kind: 'read' | 'write' | 'exec'` в схеме;
цикл агента сам спрашивает до `run`. Без `kind` — `external` → `ask`, в «Плане» скрыт.

### E1.3 Разрешение спрашивает инструмент, а не цикл — P0, 1 д
Сейчас `approve` вызывается внутри `write_file`, `edit_file`, `run_shell`,
`memory_append`. **Сделать:** перенести вызов в `runAgent` перед `tool.run`
(после валидации аргументов), инструменты получают уже разрешённый вызов.
Это база для E1.1, E1.2 и правил.

### E1.4 `run_shell` с параметром `cwd` выходит из проекта — P0, 0.5 д
`electron/lib/tools/shell.js:59`: `args.cwd || ctx.projectDir` — `cwd` не проходит
`resolveInside` и разрешается от `process.cwd()`, а не от проекта, хотя схема
обещает «относительно проекта». **Сделать:** `resolveInside(ctx, args.cwd)`.

### E1.5 Режим «Авто» = отключить разрешения — P0, 2 д
`decide()` в `auto` возвращает `allow` на всё; защищают только регулярные выражения
guardrails, которые обходятся (`powershell -enc`, `node -e`, скрипт в файле).
**Сделать:** переименовать текущий режим в «Без вопросов» (bypass) с
предупреждением и доступом только для admin; новый «Авто» — `allow` для чтения,
правок внутри проекта и команд из allowlist; `ask` для сети, git push, установки
пакетов, удаления, всего вне проекта.

### E1.6 Нет правил «разрешить всегда» — P1, 2 д
В модалке только «Разрешить / Отклонить» (`renderer/app.js:1020`). В «Вручную»
каждый `git status` — вопрос, это приучает кликать не глядя.
**Сделать:** варианты ответа как в Claude Code:
1. «Да» — один раз;
2. «Да, и не спрашивать для `<префикс команды>` / этой папки» — в сессии или проекте;
3. «Нет, и сказать агенту, что сделать иначе» — текст уходит в `tool_result`.
Правила видны и удаляются в панели «Разрешения».

### E1.7 Мёртвые записи в списке «чтение» — P2, 0.1 д
`permissions.js:55` — `web_fetch`, `web_search` числятся в `READ_TOOLS`, но таких
инструментов нет. Плагин с таким именем получит `allow` во всех режимах. Удалить.

### E1.8 Ветка `manual` в `decide()` — P2, 0.1 д
`permissions.js:115-116`: обе ветки возвращают `ask`, переменная `isUnknown`
не влияет ни на что. Упростить после E1.3.

### E1.9 Режим не применяется к уже собранному списку инструментов — P2, 0.5 д
`hidden` считается один раз (`agent.js:136`), а `approve` читает режим на каждый
вызов. Переключение «План → Вручную» посреди прогона не возвращает инструменты
записи, обратное — модель видит инструменты, которые всё равно отклоняются.
**Сделать:** пересобирать список инструментов и системную подсказку режима на
каждой итерации.

### E1.10 Журнал решений — P1, 1 д
Каждое `allow/ask/deny` с режимом, правилом и ответом — в `errors.json`-подобный
`audit.jsonl` и на доску «Качество».

## E2. Выход из «Плана» и рекомендованный вариант (P0–P1)

### E2.1 Инструмент `ask_user` с рекомендованным вариантом — P1, 2 д
Сейчас агент может только написать вопрос текстом, ответ — свободный ввод.
**Сделать:** инструмент `ask_user({ questions: [{ question, header, options:[{label, description, recommended}], multiSelect }] })`.
UI: карточка в ленте, рекомендованный вариант первым, с подсветкой и бейджем
«Рекомендуется», фокус по умолчанию, клавиши 1–4, всегда есть «Другое…».
Ответ возвращается как `tool_result`, прогон продолжается без нового сообщения.
**Приёмка:** в «Плане» агент спрашивает через `ask_user`, рекомендованный вариант
выделен визуально и выбирается по Enter.

### E2.2 План как объект, а не текст — P1, 2 д
`modePrompt('plan')` просит «альтернативы и рекомендацию» обычным Markdown, UI их не
различает, переключение режима — вручную.
**Сделать:** инструмент `exit_plan({ plan, alternatives:[{title, pros, cons, risk}], recommended })`.
UI показывает карточку плана: альтернативы плитками, рекомендованная подсвечена,
кнопки «Выполнить в режиме Вручную», «…Принимать правки», «Доработать план».
Нажатие меняет режим сессии через PolicyEngine и продолжает прогон с выбранной
альтернативой.

### E2.3 Подсветка рекомендации в модалке разрешения — P1, 0.5 д
Сейчас «Разрешить» всегда primary. **Сделать:** PolicyEngine отдаёт `risk`
(`low/medium/high`) и `recommended` (`allow` / `deny`) с причиной; для `high`
(вне проекта, удаление, сеть, push) кнопкой по умолчанию становится «Отклонить»,
подсветка и причина — в модалке.

## E4. Корректность агентного цикла и истории (P0)

### E4.1 Сообщения рантайма ломают следующий запрос к модели — P0, 0.5 д
`main.js:498,583` кладут `{ role: 'runtime' }` в `session.messages`, а `runAgent`
отдаёт историю провайдеру как есть (`toApiMessage` копирует `role`). После
OpenCode/Claude CLI в той же сессии встроенный агент получает 400.
**Сделать:** `toApiMessage` переводит `runtime` в `user`/`assistant` с пометкой
источника или исключает; тест на смешанную сессию.

### E4.2 Ошибка прогона теряет выполненные шаги — P0, 0.5 д
`main.js:857` — `session.messages = session.messages` ничего не делает: при
исключении история с уже выполненными `write_file`/`run_shell` не сохраняется, а
файлы уже изменены. **Сделать:** `runAgent` пишет историю по мере шагов
(колбэк `onStep`), при ошибке сохраняется частичная история + сообщение об ошибке.

### E4.3 Обрезка истории рвёт пары tool_call/tool — P0, 0.5 д
`trimMessages` (`agent.js:76`) режет «до следующего user», а без user — 2 сообщения.
Может остаться `tool` без родительского `assistant.tool_calls` → 400 у провайдера.
**Сделать:** резать только по границам ходов; лучше — заменить на E3.9 (сводка).

### E4.4 Ревизор пишется в историю как пользователь — P1, 0.5 д
`agent.js:273` добавляет `role: 'user'` с текстом ревизора; он сохраняется в сессии,
показывается пузырём пользователя и экспортируется как реплика человека.
**Сделать:** отдельная роль `review` в сессии, в API — как user с префиксом, в UI —
отдельная карточка «Ревизор: на доработку».

### E4.5 Имя модели в истории — текущее, а не реальное — P2, 0.2 д
`renderer/app.js:519` подписывает все старые ответы `state.model`. Сохранять `model`
в каждом `assistant`-сообщении.

### E4.6 Чат и самокоррекция идут параллельно на одной папке — P1, 1 д
`state.controller` (чат) и `state.correction` (доска) независимы; оба могут
одновременно править файлы проекта. **Сделать:** блокировка проекта на время
прогона (есть навык `resource-locks`, но в коде не используется), очередь или явный
отказ с объяснением.

## E5. Внешние рантаймы (P0–P1)

### E5.1 Режим разрешений не передаётся в CLI — P0, 1.5 д
`runtimes.js:154` запускает OpenCode/Claude/Codex/Gemini без учёта режима:
переключатель «План» ничего не значит для рантайма. **Сделать:** таблица
соответствия режим → флаги CLI (например, `claude --permission-mode plan`,
`codex --sandbox read-only`, `gemini --approval-mode`); если пресет не умеет —
селектор режима показывает «не поддерживается рантаймом» и блокирует «План».
Флаги сверить с текущими версиями CLI при реализации.

### E5.2 Prompt идёт через `cmd.exe` — P0, 1 д
`spawn(line, { shell: true })` + `winQuote`, который не экранирует `%VAR%` и
переводы строк: многострочный prompt обрезается, `%APPDATA%` раскрывается.
**Сделать:** `shell: false`, prompt — через stdin или временный файл.

### E5.3 «Все рантаймы» в одной папке — P1, 0.5 д
`runtimes:runMany` запускает несколько агентов, пишущих в один проект одновременно.
**Сделать:** по умолчанию — только чтение (E5.1) или отдельный `git worktree` на
каждый рантайм с diff в конце.

## E6. Роли и доверие проекту (P0)

### E6.1 Гость запускает агента в «Авто» — P0, 0.5 д
`chat:start`, `permissions:set`, `runtimes:run`, `mcp:connect`, `mcp:remove`,
`plugins:createExample`, `repowise:install`, `app:openExternal` — без
`requireAdmin`. Гость не может менять настройки, но может включить «Авто» и
выполнить любую команду. **Сделать:** матрица прав в одном файле, проверка в
обёртке `ipcMain.handle`; гостю — максимум `manual`, режимы `auto`/bypass скрыты и
отклоняются в main.

### E6.2 Роль переключается без прав — P1 (решение), 0.2 д
`auth:setRole` (`main.js:352`) без проверки — README честно называет это
«интерфейсным переключателем». Противоречие с E6.1: пока роль меняется в один
клик, права гостя — косметика. **Решение нужно принять:** либо локальная роль
защищена PIN/паролем ОС, либо в документации и UI честно «режим интерфейса», а
реальные права — только с Keycloak.

### E6.3 Открытие чужого репозитория запускает его код — P0, 1 д
При выборе папки `<проект>/.mai-code/plugins/*.js` импортируются в main-процесс с
полным Node (`plugins.js:20`), `<проект>/.mai-code/mcp.json` поднимает stdio-серверы
(`main.js:230`), `AGENTS.md`/`memory.md` идут в системный промпт. **Сделать:**
диалог «Доверять этой папке?» до загрузки плагинов, MCP и проектных инструкций;
список доверенных папок в настройках.

### E6.4 `sandbox: false` у окон — P2, 0.5 д
`main.js:180,209`. При `contextIsolation: true` это не катастрофа, но для окна,
которое рендерит ответы модели как HTML (`renderMarkdown` → `innerHTML`), стоит
включить `sandbox: true` и проверить санитайзер Markdown.
