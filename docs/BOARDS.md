# Доски

Четыре доски и хранилище открываются **в отдельных окнах**. «Проект ▾» → «Доски» в главном
окне открывает «Доставку», «Данные» — «Хранилище». Верхние вкладки окна доски
переключают остальные доски (каждая в своём окне).

Все доски читают один файл проекта:

```
<проект>/.mai-code/boards.json
```

Это делает состояние git-friendly: задачи, ADR, baseline архитектуры и проблемы
ревьюятся вместе с кодом. Схема секций: `delivery`, `architecture`, `runners`, `quality`.

Файл пишется атомарно, у каждой секции — номер версии (`revs`). Если доску
открыли в двух окнах и одно сохранило секцию раньше, второе получит
«Доску изменили в другом окне» и свежую версию — правку нужно повторить; правки
разных секций не мешают друг другу (ADR 0062).

## 1. Доставка

- канбан-колонки: бэклог → в работе → ревью → готово;
- drag-and-drop между колонками;
- приоритет, исполнитель, срок, описание;
- связи с артефактами хранилища (чипы открывают артефакт в окне «Хранилище»);
- ссылка на issue в Multica;
- прогресс и счётчики;
- блок «Merge requests · MAI Ship»: открытые MR проекта со статусом pipeline, ревью, steward,
  approver и расходом; через `glab api`, раз в минуту ([SHIP.md](SHIP.md#статус-mr-в-mai)).

**Multica.** [Multica](https://github.com/multica-ai/multica) — отдельное self-hosted
приложение (Go + Postgres + Next.js), а не библиотека. MAI Code не запускает его стек и
пока не синхронизирует задачи через API: доска локальная, а Multica открывается по
сохранённому URL. Это честное ограничение. Следующий шаг — клиент к API Multica, когда
будет известен стабильный контракт и запущенный экземпляр.

## 2. Архитектура

Семь представлений генерируются из одной модели в `boards.json`:

| Представление | Что показывает |
|---|---|
| C1 | система, акторы, внешние системы |
| C2 | контейнеры и связи |
| C3 | компоненты внутри контейнеров |
| C4 | классы/модули и зависимости |
| Sequence | сценарий запроса к агенту |
| ER | сущности, атрибуты, кардинальности |
| Deployment | узлы, VM/контейнеры, CPU, RAM, GPU |
| OpenAPI | эндпоинты, методы, теги, спецификация |

- **Mermaid** рисуется локально (пакет `mermaid`, без сети).
- **PlantUML** генерируется и экспортируется кнопкой «Экспорт .puml». Встроенный
  рендер PUML не подключён: для него нужен Java и PlantUML-сервер, которых мы не
  предполагаем на машине. Экспорт открывается в IDE/PlantUML-плагине.
- **Baseline** фиксирует хеши всех представлений и git HEAD. Если модель или git
  изменились, доска показывает баннер дрейфа и помечает конкретные представления.
- **ADR** создаются как артефакты `adr:*` с версиями и статусом
  `proposed / accepted / rejected / superseded`.
- **Модель** редактируется как JSON: контейнеры, компоненты, связи, sequence, ER,
  deployment, OpenAPI. После сохранения все представления пересчитываются.
- **Калибровка** («Откалибровать», ADR 0090): модель сверяет `docs/PRD.md`, модель
  C1–C3, ADR и OpenSpec и возвращает таблицу находок — противоречия, пробелы,
  риски, вопросы к продукту, с важностью и источниками. Отчёт — артефакт
  `calibration:architecture` с версиями; повторный запуск показывает, что
  появилось и что ушло. Это советник, а не гейт.

Ограничения: C4 — упрощённая class diagram, а не полный код-граф; drift считается по
хешу сгенерированного текста, а не по семантическому diff; автоматического импорта
архитектуры из кода нет.

## 3. Рантаймы и деплой

- стадии конвейера (сборка, тесты, пакет, деплой) с редактируемой shell-командой;
  команда лежит в `boards.json` проекта, поэтому стадии запускаются только в
  доверенной папке (ADR 0028); вывод с кириллицей на Windows читается корректно;
- запуск/остановка стадии, живой журнал, код возврата, время последнего запуска;
- git: ветка, HEAD, dirty-файлы, ahead/behind, diff по файлу;
- список внешних рантаймов из настроек и признак занятости;
- ошибки стадий попадают в журнал `errors.json` и на доску качества.

«Агентный деплой» реализован как управляемый конвейер: команда стадии может вызывать
любой пайплайн, а MAI Code показывает состояние и сохраняет журнал. Автоматического
оркестратора с политиками (canary, approvals, rollback) нет — это следующий слой.

## 4. Качество и самокоррекция

Скан проверяет:

- дубли имён и почти одинаковое содержимое артефактов (Jaccard по токенам);
- навыки с одинаковыми именами и почти совпадающим телом;
- одинаковые и противоречащие строки в проектном и глобальном `AGENTS.md`
  (эвристика «всегда ↔ никогда», «always ↔ never»);
- коллизии имён инструментов в плагинах;
- повторяющиеся ошибки агента/рантаймов из `errors.json`;
- битые ссылки задач на артефакты.

Действия: игнорировать проблему, открыть связанный артефакт, запустить
**self-correction loop** для выбранных проблем. Агент получает список проблем и
открытые задачи, читает файлы, вносит правки (каждое действие подтверждается),
после чего автоматически запускается повторный скан. История циклов хранится в
`quality.corrections`.

Ограничения: эвристики, а не формальный анализ; «почти одинаковое» содержимое может
давать ложные срабатывания; противоречия ищутся по ограниченному набору антонимов;
diff — построчный LCS, без семантики.

## Хранилище

Пятое окно — не доска, а интерфейс к артефактам и инфраструктуре:

- список и поиск, редактор, история версий, diff, восстановление;
- импорт из файловой системы, экспорт, запись в привязанный файл;
- статус Postgres/pgvector, Vault, SeaweedFS, ручная синхронизация и поиск;
- статус Repowise, установка, индексация, MCP, дашборд.

Подробности — [STORAGE.md](STORAGE.md) и [REPOWISE.md](REPOWISE.md).

## События и связность

Окна общаются через main-процесс:

- `board:event` — поток самокоррекции и стадий (`delta`, `tool_call`, `approval`,
  `stage:chunk`, `stage:exit`, `correction:done`);
- `board:focus` — открыть окно с фокусом на артефакте, ADR или стадии;
- `boards:*`, `artifacts:*`, `infra:*`, `repowise:*` — IPC-неймспейсы.

Окна не разделяют React-состояние: каждое перечитывает `boards.json` при открытии и
после действий. Это просто и надёжно, но изменения в одном окне не появляются в другом
мгновенно — нужно нажать «Обновить».
