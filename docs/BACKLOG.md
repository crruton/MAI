# Бэклог

Состояние на 05.11.2026. Здесь собраны крупные направления с критериями приёмки и
честными ограничениями. Часть пунктов уже закрыта — статус указан в таблице и в
разделе. Порядок внутри приоритета — рекомендуемая последовательность работ, а не
жёсткий план.

Обозначения приоритетов:

- **P1** — даёт заметную пользу при малой цене, делаем первым.
- **P2** — важно, но требует отдельного дизайна или внешних зависимостей.
- **P3** — исследовательское или инфраструктурное направление, нужен бизнес-кейс.

## 1. Полная GitBook-документация, встроенная в приложение

**Статус: сделано.** `docs/SUMMARY.md` — оглавление, `electron/lib/docs.js` читает
документацию из `app.getAppPath()/docs`, панель «📖 Документация» показывает дерево,
содержание и поиск. `npm run docs:check` проверяет ссылки и страницы вне оглавления.
Не сделано: версии страниц и совместное редактирование — документация обновляется
вместе с кодом.

**Зачем.** Раньше документация была набором Markdown-файлов в `docs/`. Пользователь не видел
её из интерфейса, а разработчик не мог поддерживать единое оглавление и версии.

**Объём.**

- Единое оглавление (`docs/SUMMARY.md`) и структура разделов: обзор, установка, провайдеры,
  рантаймы, доски, хранилище, Repowise, инфраструктура, безопасность, FAQ.
- Сборка GitBook-совместимого дерева (Markdown + `SUMMARY.md`), без обязательного облака
  GitBook: сборка локальная, публикация — опционально.
- Новое окно «Документация» (или вкладка в «Хранилище») с навигацией по разделам,
  поиском и рендером Markdown/Mermaid.
- Проверка ссылок и «сиротских» страниц в CI.

**Критерии приёмки.**

- Из приложения открывается окно документации, все разделы доступны без интернета.
- `docs/SUMMARY.md` — единственный источник оглавления; добавление страницы без записи
  в оглавление валит проверку.
- Внутренние ссылки проверяются скриптом, битых ссылок — 0.
- Документация версионируется вместе с кодом и попадает в релизный артефакт.

**Ограничения.** GitBook Cloud не обязателен; встроенный просмотрщик — это собственный
рендер, а не полный GitBook (без плагинов и интерактивных блоков). Тяжёлые диаграммы
рендерятся так же, как на доске архитектуры (Mermaid локально, PlantUML — экспорт).

## 2. herdr как калибратор архитектуры и PRD

**Зачем.** Нужен внешний «второй взгляд» на архитектуру и PRD: herdr уже установлен и
подключён как рантайм, но используется только как обычный агент.

**Объём.**

- Пресет «Калибратор»: отдельная команда, которая получает PRD, C1–C3, ADR и список
  открытых вопросов, а возвращает структурированный отчёт (противоречия, пробелы,
  риски, вопросы к продукту).
- Кнопка «Откалибровать» на доске «Архитектура»: собирает контекст из артефактов,
  запускает herdr, результат сохраняется как артефакт `note` с версией.
- Сравнение «до/после»: отчёт привязывается к baseline, повторный запуск показывает,
  что изменилось.
- Формат ответа фиксирован (JSON или Markdown-шаблон), чтобы результат можно было
  показать в таблице, а не только текстом.

**Критерии приёмки.**

- На доске есть запуск калибровки, виден прогресс и журнал.
- Результат сохраняется в хранилище и связан с задачей доставки.
- Повторный запуск на том же baseline даёт diff отчётов.
- Ошибка herdr не ломает доску: показывается сообщение и кнопка повтора.

**Ограничения.** Качество отчёта зависит от модели и полноты входных артефактов.
herdr не гарантирует детерминизм, поэтому «калибратор» — это советник, а не гейт.
Нужен явный лимит токенов и таймаут.

## 4. `memory.md`, подключённый к агенту

**Статус: сделано.** Файлы `<проект>/.mai-code/memory.md`
и `%APPDATA%\mai-code\memory.md` создаются и читаются, панель «Память» показывает и
редактирует их, содержимое попадает в системный промпт. Версии и откат сделаны
(ADR 0024, `electron/lib/memory.js`). Инструменты агента `memory_read` и
`memory_append` сделаны (`electron/lib/tools/memory.js`, 40 проверок в
`scripts/test-memory-tools.mjs`).

**Зачем.** Агенту не хватает долговременной памяти о проекте: решения, договорённости,
известные грабли. `AGENTS.md` — это инструкции, а не накопленный опыт.

**Объём.**

- Файл `<проект>/.mai-code/memory.md` (и глобальный `%APPDATA%\mai-code\memory.md`).
- Подмешивание памяти в системный промпт с лимитом по размеру и приоритетом:
  проектная память → глобальная → `AGENTS.md`.
- Инструменты агента `memory_read` / `memory_append` с подтверждением записи.
- UI: просмотр и редактирование, история версий через хранилище артефактов.
- Автоматическое предложение записать вывод после успешной задачи (не автосохранение).

**Критерии приёмки.**

- Память видна в промпте (отладочный вывод), не превышает заданный лимит.
- Запись создаёт версию артефакта, откат работает.
- Пользователь может отключить память в настройках.
- Нет дублей: повторная запись одинакового текста не плодит версии.

**Ограничения.** Память — это текст, а не база знаний; поиск по ней — подстрочный.
Автоматическое «запоминание» может накапливать мусор, поэтому по умолчанию только
явные записи.

## 5. Скрепка для загрузки файлов в диалог

**Статус: сделано.** `electron/lib/attachments.js` (ADR 0016), IPC `attachments:*`,
кнопка `#attach` в композере, drag-and-drop, чипы с именем и размером, лимиты
200 МБ на файл / 500 МБ суммарно / 20 файлов, чистка при удалении сессии
(`removeSessionUploads`), `.gitignore` для `.mai-code/uploads/`. Индикатор
суммарного размера и числа файлов — в композере. Тесты:
`scripts/test-attachments.mjs` — 35 проверок.

**Зачем.** Сейчас в чат можно вставить текст, но нельзя приложить файл. Для логов,
скриншотов и таблиц это блокер.

**Объём.**

- Кнопка-скрепка в композере: выбор файлов, drag-and-drop, вставка из буфера.
- Поддержка текста, изображений (превью), PDF и таблиц; лимит размера и типов.
- Файлы копируются в `<проект>/.mai-code/uploads/<session>/` и передаются агенту
  как вложения (изображения — в мультимодальном формате, текст — извлечённым текстом).
- Чистка вложений при удалении сессии, индикатор размера.

**Критерии приёмки.**

- Файл прикрепляется, отображается чипом с именем и размером, удаляется до отправки.
- Агент получает содержимое: текст — целиком в пределах лимита, изображение — как image.
- Превышение лимита даёт понятную ошибку, приложение не падает.
- Вложения не попадают в git (`.gitignore`).

**Ограничения.** DOCX/XLSX/PDF требуют парсинга; на первом этапе — только текст,
изображения и PDF-текст. Большие файлы обрезаются с явным предупреждением.
Провайдер должен поддерживать мультимодальные запросы; иначе изображения
конвертируются в текст или отклоняются.

## 6. Скачивание ответа в md, txt, docx и excel

**Зачем.** Ответы агента часто нужно отдать наружу: в документ, отчёт или таблицу.

**Объём.**

- Меню «Скачать» у сообщения и у всего чата: Markdown, TXT, DOCX, XLSX.
- Markdown/TXT — без зависимостей; DOCX — через библиотеку (`docx`), XLSX — через
  `exceljs` или генерацию SpreadsheetML.
- Для таблиц в ответе — отдельный лист Excel; для кода — блок с моношрифтом.
- Имя файла: `<дата>-<тема>.md`, безопасное для Windows.
- Диалог сохранения через Electron `dialog.showSaveDialog`.

**Критерии приёмки.**

- Все четыре формата открываются в соответствующих программах без предупреждений.
- Кириллица и эмодзи не ломаются (UTF-8, BOM только где нужно).
- Таблицы из Markdown попадают в Excel отдельными колонками.
- Экспорт работает офлайн и не требует сервера.

**Ограничения.** DOCX/XLSX — это конвертация Markdown, а не полноценная вёрстка:
сложные диаграммы и вложенные таблицы упрощаются. Формулы Excel не генерируются.

## 7. Вывод на домен и бесплатное доменное имя

**Статус: частично.** Сделан статический лендинг `site/`, workflow GitHub Pages
`.github/workflows/pages.yml`, инструкция `docs/DOMAIN.md`. Своего домена и TLS
в репозитории нет — это настройка владельца. Веб-клиента нет.

**Зачем.** Нужна публичная точка входа: скачать приложение, открыть документацию,
посмотреть демо.

**Объём (поэтапно).**

1. Статический сайт: лендинг + документация + релизы. Хостинг: GitHub Pages / Cloudflare
   Pages. Бесплатный домен: поддомен `*.pages.dev` или `*.github.io`, либо бесплатный
   домен первого уровня от провайдера (например, `.eu.org`, `.is-a.dev`) — с оговоркой,
   что это не коммерческий бренд.
2. Web-версия чата — только если появится серверная часть (см. п. 8). Electron-приложение
   работает на `file://` и на домен «просто так» не переносится.
3. TLS, редиректы, базовая аналитика без трекеров.

**Критерии приёмки.**

- Сайт открывается по HTTPS, есть страницы «Скачать», «Документация», «Ограничения».
- Ссылки на релизы ведут на GitHub Releases.
- Домен и DNS описаны в документации; переезд на другой домен — одна переменная.
- Нет секретов в статике, CSP настроена.

**Ограничения.** «Бесплатное доменное имя» — это поддомен или бесплатный TLD, а не
брендовый `.com`. Полноценный веб-клиент требует серверной авторизации, хранения
сессий и ключей — это отдельный проект, а не деплой текущего Electron-приложения.
Домены `.eu.org` и подобные требуют ручного подтверждения и не гарантируют SLA.

## 8. Ролевая модель Админ/Гость через Keycloak

**Статус: частично.** Реализованы локальные роли admin/guest, OIDC Device
Authorization Grant с PKCE (S256), извлечение ролей из JWT, шифрование токенов через
`safeStorage`, проверка прав в main-процессе для опасных IPC. В `infra/keycloak/` лежит
realm и compose. Проверено: realm импортируется, device endpoint принимает запрос с
`code_challenge`, опрос токена возвращает `authorization_pending` до подтверждения
входа. Не сделано: серверный режим, экран логина «только вход», автотесты матрицы
прав, продакшен-профиль Keycloak.

**Зачем.** Нужно разграничение доступа: администратор управляет проектами, провайдерами
и инфраструктурой, гость видит только выданные проекты и не может менять настройки.

**Объём.**

- Keycloak как OIDC-провайдер: realm, клиенты `mai-code-desktop` и `mai-code-web`,
  роли `admin` / `guest`.
- В приложении — вход через Authorization Code + PKCE, хранение токенов в защищённом
  хранилище ОС (Electron `safeStorage`), refresh, выход.
- Матрица прав: что доступно гостю (чтение досок, чат в рамках проекта, экспорт)
  и что только админу (провайдеры, ключи, инфраструктура, установка рантаймов,
  удаление артефактов).
- Проверка прав на уровне IPC, а не только в UI.
- Локальный режим без Keycloak сохраняется (single-user, роль admin).

**Критерии приёмки.**

- Без входа в корпоративном режиме доступен только экран логина.
- Гость не может вызвать админский IPC даже вручную (проверка на бэкенде).
- Токены не попадают в логи и `settings.json`.
- Есть тесты матрицы прав и инструкция по развёртыванию Keycloak.

**Ограничения.** Keycloak — серверное ПО; для одного пользователя на одном компьютере
он избыточен. Полноценная модель требует серверной части, иначе права проверяются
в локальном процессе и не являются защитой от владельца машины. Нужен отдельный
этап «серверный режим».

## 9. Анализ: OpenScion, Harness2, Delamain

Короткий ответ: **полностью — нет, частично — да, и только точечно.** Ни один из трёх
проектов не заменяет текущую архитектуру MAI Code, и каждый тянет за собой несовместимый
стек или модель эксплуатации.

### OpenScion — не добавлять

- **Что это.** Серверная система контроля версий для очень больших монорепозиториев,
  где клиенты — агенты и CI, а не люди. Rust, GPL-3.0. Сервер делает rebase/merge,
  changeset'ы вместо снапшотов, контентная адресация BLAKE3.
- **Почему не подходит.** Это замена git и серверный продукт, а MAI Code — локальный
  десктоп-клиент поверх обычного git-репозитория. GPL-3.0 несовместима с MIT-лицензией
  проекта при встраивании кода. Пользователю пришлось бы мигрировать репозиторий
  и держать сервер — ради задачи, которой у нас нет (десятки тысяч агентских checkout'ов).
- **Что взять концептуально.** Идею «changeset = только изменённые файлы» и контентной
  адресации — она уже частично есть в хранилище артефактов (content-addressed блобы).
  Полезно для будущего инкрементального diff'а досок.
- **Решение.** Не встраивать. Пересмотреть, только если появится серверный режим
  с монорепозиторием и агентским CI.

### Harness2 (Harness?) — не добавлять зависимостью, перенять идеи

- **Что это.** Исследовательский фреймворк Google Research для «рекурсивного
  харнессинга»: агент правит собственный harness (промпты, инструменты, память)
  через Propose-Probe-Compose, а второй уровень рекурсии накапливает улучшения.
  Python 3.12, Apache-2.0, ориентация на Linux и бенчмарки.
- **Почему не подходит как зависимость.** Это не библиотека для встраивания в Electron,
  а стенд для экспериментов с бенчмарками. Требует Python-окружения, GPU-ресурсов
  и воспроизводимых прогонов; его результаты не гарантируют улучшения на реальных
  задачах пользователя.
- **Что взять.** Идею **редактируемого harness**: пресеты агента (промпт, набор
  инструментов, лимиты) как версионируемые артефакты с A/B-сравнением на одинаковых
  задачах. Это ложится на доски «Качество» и «Хранилище» без Python-зависимости.
- **Решение.** Частично: добавить в бэклог «версионируемые профили агента и сравнение
  прогонов». Полную интеграцию не делать.

### Delamain — ближе всего, но позже и частично

- **Что это.** Локальный диспетчер для Claude Code / Codex: брифинги, воркеры по ролям,
  журналы, inbox'ы, блокировки общих ресурсов, handoff между сессиями. Python, MIT.
  Ориентация на macOS/Linux, на Windows — через WSL.
- **Почему не подходит целиком.** Это плагин чужого CLI с хуками и собственным форматом
  состояния; на Windows требует WSL. Встраивание в Electron означало бы тащить Python
  и чужой протокол.
- **Что взять.** Паттерны, которые прямо нужны доскам 3–4:
  - журнал решений и handoff между сессиями (аналог `memory.md` + журнал задач);
  - locks на общие ресурсы (папки, ветки, окружения) перед запуском стадий;
  - inbox/owner questions для асинхронных уточнений;
  - «progress view» — сводка по воркерам.
- **Решение.** Частично и позже: реализовать locks и handoff в `boards.json` и
  `memory.md`. Полную интеграцию не делать, пока нет кроссплатформенного ядра.

## 10. Установщики: exe, docker-compose, tar

**Статус: сделано.** Добавлены `electron-builder.yml`, скрипты `dist`, `dist:win`,
`pack:offline`, `pack:tar`, workflow `.github/workflows/release.yml`,
`infra/docker-compose.yml` и `scripts/make-offline.mjs`. Офлайн-TAR содержит
`node_modules` и Electron, поэтому запускается без сети. Ограничения остались:
EXE не подписан, docker-compose поднимает только инфраструктуру.

**Зачем.** Раньше запуск был только из исходников. Нужны три способа установки под разные
сценарии: обычный пользователь Windows, сервер/команда, офлайн-перенос.

**Объём.**

- **EXE (NSIS)** через `electron-builder`: portable и установщик, иконка, ассоциации
  файлов не обязательны, автообновление — позже. Подпись кода — по возможности.
- **docker-compose**: образ приложения (или только инфраструктура: Postgres/pgvector,
  Vault, SeaweedFS) + инструкция. Для GUI нужен X11/WSLg или web-режим; честно описать.
- **TAR-дистрибутив**: `mai-code-<version>-win-x64.tar.gz` с `node_modules`, `electron`,
  документацией и скриптом `install.ps1`; офлайн-установка без npm.
- GitHub Actions: сборка по тегу, артефакты в Release, контрольные суммы SHA-256.

**Критерии приёмки.**

- По тегу `v*` CI собирает три артефакта и прикрепляет к Release.
- Установленный EXE запускается на чистой Windows 10/11 без Node.js.
- TAR распаковывается и запускается без сети.
- `docker-compose up` поднимает инфраструктуру, приложение подключается к ней.
- В README — таблица «способ / требования / что внутри».

**Ограничения.** EXE без подписи вызывает предупреждение SmartScreen. Docker с GUI
на Windows нетривиален: образ с Electron требует WSLg, поэтому docker-compose в первую
очередь для инфраструктуры и серверного режима. TAR — большой (Electron ~150 МБ).

## 11. Свой VPN hub

**Статус: частично.** Добавлен `infra/vpn/docker-compose.yml` на wg-easy/WireGuard:
выдача конфигов, QR, отзыв клиентов. Не сделано: роли VPN, аудит, ротация ключей,
интеграция с Keycloak, runbook и проверка на реальном сервере.

**Зачем.** Нужен управляемый доступ к внутренним сервисам (Postgres, Vault, раннеры)
без публикации их в интернет.

**Объём (минимум).**

- Хаб на WireGuard: генерация ключей, конфиги клиентов, QR, отзыв доступа.
- Роли: админ (все узлы), разработчик (проектные сервисы), гость (только UI).
- Аудит подключений, лимиты, ротация ключей.
- Интеграция с ролевой моделью (п. 8): доступ к VPN = отдельная роль.

**Критерии приёмки.**

- Клиент подключается, видит только разрешённые подсети.
- Отзыв ключа немедленно закрывает доступ.
- Конфиги не хранятся в git, ключи — в Vault.
- Есть runbook: развёртывание, бэкап, ротация, инцидент.

**Ограничения.** Это инфраструктурный продукт, а не функция приложения. Нужны сервер,
юридическая оценка (трафик, персональные данные, экспорт), дежурство и мониторинг.
Для одного пользователя проще Tailscale/Cloudflare Tunnel; свой хаб оправдан только
при нескольких командах и требовании полного контроля.
